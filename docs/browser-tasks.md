# Browser-assisted tasks

Some chores have no API: filing an expense report, filling in a weekly time sheet. blumkin handles them by driving a browser **you** sign in to, filling in the form for you and then stopping. blumkin has no submit command, and a browser task ends by telling you exactly what to review and which button to press. The guard blocks the listed submit paths; the Limits section lists the cases it does not block.

## How it works

1. You create a dedicated browser profile for the task and launch it. You sign in by hand, SSO and MFA included. blumkin never sees, types or stores your credentials; the session cookies live only in that profile directory.
2. An agent (or you) runs the task's skill, which attaches to that browser over the Chrome DevTools Protocol (CDP) with [Playwright](https://playwright.dev/python/), reads the page, fills in fields and uploads files.
3. The task ends with a handoff: what was filled in, what still needs your decision, and numbered steps for the final click. The result always says `submitted: false`.

Chrome, Edge and Chromium are supported. blumkin uses the browser already installed on your machine and never downloads one.

## Set up a task

Create the task's profile and tell blumkin which controls it may click.

```bash
blumkin browser profile create expense-report
```

Then add the task's policy to `~/.config/blumkin/config.toml`.

```toml
[browser]
default = "edge"          # chrome | edge | chromium; Chrome is used when unset or not installed

[browser.tasks.expense-report]
allowed_controls = ["Add line", "Create report"]   # exact names the form shows; `*` stands for any text
extra_deny_names = ["release"]                     # optional; adds to the built-in list
dialog_confirm = ["OK"]                            # optional; confirm buttons that are valid only inside a dialog
form_url = "https://erp.example.com/expenses"      # optional; what `goto` and `launch --open` open
sign_in_hosts = ["sso.example.com"]                # optional; extra identity-provider hosts `goto` waits through
upload_dirs = ["~/Documents/receipts"]             # folders `upload` may read from; none = no uploads
download_dirs = ["~/transcripts"]                  # folders `download` may save into; none = no downloads
allowed_hosts = ["erp.example.com"]                # sites `upload` may send to; also limits `goto`
block_background_writes = false                    # optional strict mode, off by default; see below
```

The `[browser]` and `[browser.tasks.*]` tables go anywhere in `config.toml`, next to your `[profiles.*]` tables. If every command instead fails with `named [profiles.*] layout cannot mix top-level flat keys (browser)` although the file is valid TOML, your blumkin build predates that support (release 1.13.0 is such a build, and so are the `[loop]` and `[cron]` tables on it): check `blumkin --version`. `blumkin upgrade` fixes it once a release newer than 1.13.0 is published; until a release newer than 1.13.0 is published, run the checkout with the dev launcher (`scripts/dev/blumkin`, see the `blumkin-dev` skill) or wait for that release.

`allowed_controls` is what makes `blumkin browser click` work for the task: a control that is not listed is refused, and the refusal lists the names and patterns the task does declare. A name may contain `*` for any text, so one entry such as `"Actions for * Report"` covers a control whose name carries the trip's own name (a saved report's actions link), with no config edit per trip. A pattern must start with fixed text (no leading `*`), hold at most two `*` (only an ASCII `*` is a wildcard) and keep at least four letters or digits of fixed text, and that fixed text cannot be a finalizing word (`"Submit *"` is refused when the task is used). The name actually clicked is still checked against the built-in finalizing words (submit, send, pay, confirm, file, complete, finish, approve, ...), so a pattern never reaches those; names such as `Delete` or `Duplicate` are not on that list, so they stay out of reach only because a menu item is declared one by one, exactly (`Open` yes, `Delete` no): keep the fixed text of a pattern specific, and add such words to `extra_deny_names` if a page could show them in a name your pattern would match. Everything else about a matched control is unchanged: it is vetted like any other, and a duplicate name still needs `--nth`. `extra_deny_names` can only add to the built-in list of finalizing words, never shorten it. `dialog_confirm` lists exact names of buttons that confirm a dialog's own rows (an attachments dialog's `OK`, which is usually a submit-type button and would otherwise be refused as a submit control): such a button may be clicked only when it sits inside a dialog (`<dialog>`, `role=dialog` or `alertdialog`) whose form, if it has one, lies inside that same dialog, so a dialog nested in the report's own form never qualifies, and a dialog that also holds a finalizing control (a modal wrapped around the whole report and its own `Submit`) never qualifies either; `OK` itself is not on the built-in list of finalizing words, it is refused only because it is usually a submit-type button, and a page that marks a wrapper as a dialog is judged by what that dialog holds; the same name anywhere else is refused, and a name that is a finalizing action (`Submit`, `Pay`, `Send`, `Confirm`, ...) can never be listed, so the report's own `Submit` stays out of reach. A formaction override, a script link or a submitting click handler is still refused on it. A dialog confirm needs no entry in `allowed_controls`. `upload_dirs` is where the task may upload files from (absolute folders, or folders starting with `~/`, but never `/`, the whole home directory or a path that climbs out of it; `~user` paths are refused) and `allowed_hosts` is where it may send them (`erp.example.com`, or `*.example.com` for any subdomain, which needs a dot after the star, though public suffixes such as `co.uk` are not checked); with either missing `blumkin browser upload` refuses every file, so a page cannot make an agent upload an arbitrary file such as a key or a token, or send a receipt to another site. `download_dirs` is the same for `blumkin browser download`: where a file the page offers may be saved (default deny). Once a task declares hosts, `blumkin browser goto` refuses any other host too and every other command refuses to act on a page outside them; with no `allowed_hosts`, `goto` is not limited at all, so declare them. An unknown key in a task table is an error, so a typo such as `allowed_control` does not silently leave the task with an empty allow list. Everything that belongs to you personally (the form URL, your receipts folder, your categories, your default weekly hours) lives in your own task definition, not in blumkin; see [`operator-config.md`](./operator-config.md).

`block_background_writes` is an opt-in strict mode for simple forms, off by default. While a command is attached, the safety net then also answers every other write (`fetch`, `XMLHttpRequest`, a beacon) with an empty response, so a handler on a control you declared cannot post form data in the background; the server never receives it. It breaks pages that need background writes to work: an ERP page that sends almost every interaction, including adding a line, as a background POST will appear to do nothing, so leave it off for those. There is no matching setting for GET form submissions: the browser does not expose whether a navigation came from a form or from a link, so blumkin cannot tell a form GET from a link with a query string, and blocking every navigation with a query string would break ordinary browsing. Strict mode covers requests the page makes while blumkin is attached; a request a service worker makes itself is routed, but a page request that a service worker answers is not seen by the route, and neither are WebSocket messages or hyperlink pings, so "every write" here means every HTTP write the browser lets blumkin route.

### Telling which window an agent is driving

Each task has its own colour, derived from the task name (`colour` in `blumkin browser status`, `launch` and `endpoint`, always the same for a task). Whenever blumkin attaches, the page it is on shows a small `blumkin - TASK` pill in the bottom left corner in that colour, with a thin line of it along the top edge, so the window an agent is driving is recognizable at a glance. The mark takes no clicks, is hidden from the page text and the accessibility tree that `browser read` returns, is added through the browser's style API so a page's content security policy does not block it, and is only added to a page on an allowed host (never to a sign-in page or a blocked one; the page's own address is checked in the same step that adds it). The `explore` and `model check` commands show it too. The colour is dark enough for the white text to meet the 4.5:1 contrast of WCAG AA. It stays until the page navigates and is put back by the next command; closing the browser closes the window and the mark with it. Commands attach one at a time and detach in between, so the mark is not removed on each detach: it belongs to the window for as long as the window lives.

### Signing in, the first page and the endpoint

`blumkin browser launch TASK --open` starts the browser and opens the task's `form_url` in one step (any other address goes through `blumkin browser goto TASK URL`). A site that sends the page to an identity provider (login.microsoftonline.com, login.microsoft.com, login.live.com, accounts.google.com, or a host in the task's `sign_in_hosts`: an Okta, Auth0, OneLogin or Ping tenant is named there, for example `acme.okta.com`, because anyone can register such a tenant) is waited through by `launch --open` and by `blumkin browser goto TASK [URL]`: only the page address is polled, for up to `--sign-in-wait` seconds (default 120, `0` to not wait), while you sign in by hand, nothing is ever done on the sign-in page, and the command carries on as soon as the page is on an `allowed_hosts` host, so nobody has to say they are signed in. If the time runs out on the sign-in page (`sign_in_timeout`), sign in and run `goto` again; the result names the host that was waited on (`sign_in_host`) and how long (`waited_for_sign_in_s`). A `form_url` must be an https address on one of the task's `allowed_hosts`. `blumkin browser status` shows how many pages the browser has open: a browser with no open page is running but cannot be driven, so the status says so, and the next browser command opens a blank page for you (`browser_no_page` says what to do when that fails, `browser_attach_failed` when the attach itself fails, `browser_not_running` when nothing was launched). The DevTools port changes on every launch: `blumkin browser endpoint TASK` prints it, and `status --json` carries it too. After `blumkin browser close` and a new launch the identity provider's session cookies may be gone: cookies it sets without an expiry (session cookies) are dropped when the browser closes, so you may have to sign in again, and keeping the browser open between runs is what keeps the sign-in. A site that sets persistent cookies keeps the session in the task profile across launches.

## Run a task

Launch the browser, sign in by hand in the window that opens, then let the skill drive it.

```bash
blumkin browser launch expense-report
blumkin browser goto expense-report https://erp.example.com/expenses
blumkin browser read expense-report
blumkin browser fill expense-report "Amount" "12.50"
blumkin browser upload expense-report "Receipt" ~/Documents/receipts/taxi.jpg
blumkin browser select expense-report "Type" "Taxi"
blumkin browser click expense-report "Add line"
blumkin browser handoff expense-report --filled "1 line, 12.50 USD" --step "Review the line and the total." --step "Press Submit at the bottom right."
```

Each command attaches to the running browser, does one thing and detaches; the browser stays open with your session. `blumkin browser click` finds the control by name; pass `--role` (`--role link`, `tab` or `menuitem`) to choose when the name exists in more than one role, for example `blumkin browser click expense-report "Help" --role link`. The two ready-made skills are [`expense-report`](../.agents/skills/expense-report/SKILL.md) and [`time-sheet`](../.agents/skills/time-sheet/SKILL.md).

`blumkin browser click` without `--role` finds the control by its name across the clickable roles and says which role it found; a name that exists in more than one role, or two controls of one name within a role, is refused until you pass `--role` or make the name unique (a second role appearing after the first poll found a match is not seen). When a page legitimately repeats a name (a list that has a "More actions" button on every row), `--nth N` says which one is meant: N is 1-based, in DOM order (the order `browser read --aria` lists them, which can differ from the visual order), and the click is refused with the real count when the page has fewer than N within `--wait`. `--nth` is for `click` only; `browser download` still refuses a repeated name. `--nth` does not change what a task may click: the name must still be declared, a finalizing name is still refused, and the element it picks is vetted before the click. Page order can change between loads, so read the page (`browser read --aria`) before relying on a position, and prefer a unique name when there is one. It waits up to `--wait` seconds for the control: 5 by default when finding it by name, so a missing control fails in seconds, and 30 (the action timeout) when `--role` is given; `--wait` is capped at 300. `blumkin browser refresh-tab TASK TAB --via OTHER` reloads a pane that only reloads when another tab is shown first: both tabs must be declared in `allowed_controls` (checked before the first click), it selects `OTHER`, checks the page is still on an allowed host, then selects `TAB` again; if the second step fails the error says the page was left on `OTHER`. `blumkin browser read TASK --frame N --wait SECONDS` waits for a frame that attaches late (and, for text, for it to have text) instead of reading it empty; a read that fails while the frame is still navigating is retried until the wait is over.

### Fields the page repeats, dropdowns and frames

`blumkin browser fill`, `select` and `upload` find a field by its label. When the page repeats a label (a second Date, Type and Amount appears once the report has an item), the command refuses and lists every match with its role and accessible name; narrow it with `--exact` (the whole label), `--role` (look it up by accessible role and name) or `--nth N` (1-based, in DOM order, the order `blumkin browser read TASK --aria` lists them), as `click` does. `blumkin browser select TASK LABEL OPTION` chooses an option in a native dropdown or an ARIA combobox and refuses an option or field named like a finalizing action; a combobox and its option are vetted like a click (a submit control is refused) and `--role` for it is one of combobox, listbox, searchbox or textbox. `--frame N` (a number from `blumkin browser frames TASK`, pinned with `--host`) works inside a child frame such as an attachments dialog, which must be on a host in `allowed_hosts`; uploads there still go only from the task's `upload_dirs`. `fill` and `select` check what the field holds afterwards: `matches` says whether it is exactly what was set, and when it is not (an autocomplete expanded the text to a canonical form, or rewrote it) the field's value is returned as `read_back`; what was set is never echoed back and a password field is never read.

### Look inside a page: frames and the ARIA snapshot

Some panes are not in the page text. `blumkin browser frames TASK` lists the page's child frames: a 1-based number, the host, the origin (never the path or query) and whether the task's `allowed_hosts` accept it. `blumkin browser read TASK --frame N` reads that frame's text (untrusted data, like any page text); it needs `allowed_hosts` and refuses a frame on any other host. `blumkin browser read TASK --aria` returns the ARIA snapshot (roles and accessible names) of the page, or of the frame with `--frame N`: use it to learn a control's name and role before declaring it in `allowed_controls`. Link addresses and field values are removed from it; hidden and screen-reader-only text is not, so it is untrusted data, and a page snapshot stops at frame boundaries. A frame in another origin shows up a moment after it attaches, so `browser frames` waits up to `--wait` seconds (default 2) for one; `--wait 0` lists what is there at once. Every command attaches to the browser fresh, and Playwright does not list a cross-origin frame that already existed when it attached, so blumkin also reads Chrome's own list of frame targets (`/json/list`, on the same loopback endpoint) and talks to such a frame over its own DevTools socket: only on this machine, only to evaluate a script in it, and under the same `allowed_hosts` checks. A frame whose address Playwright already lists is taken from Playwright, and at most 32 such frames are read. Frames reached that way have no ARIA snapshot (`--aria` with `--frame` says so); read their text instead. Frame numbers shift when the page adds or reloads a frame, so list them again before reading, and pass `--host HOST` with `--frame` to refuse any other frame.

## Start a task from a template

`blumkin browser init-task [TASK] --template teams-transcript` creates the task's browser profile and prints the `[browser.tasks.TASK]` table the template starts from: the hosts the site uses (for Teams that includes the SharePoint host its transcript pane is served from) and the navigation controls the task may click. Nothing is written to `config.toml` unless you add `--yes`, which appends the table (creating the file with mode 0600 if it is missing); a table of that name that already exists is never changed, and a `config.toml` that is not valid TOML, or is a symlink, is left alone. The template's `*.sharepoint.com` covers every organization's SharePoint: narrow it to your tenant's host once you know it. The ready-made skill for the Teams template is [`teams-transcript`](../.agents/skills/teams-transcript/SKILL.md). For an expense report, `blumkin browser init-task --template expense-report --host erp.example.com --form-url https://erp.example.com/expenses --upload-dir ~/Documents/receipts --yes` writes the whole `[browser.tasks.expense-report]` table in one go, with no hand-editing of `config.toml`: your host (it differs per organization, so `--host` is required), the controls of the Oracle Fusion Expenses flow (`Create Report`, `Create Item`, `Save and Close`, `Manage Attachments`, `Add Row`, `Save`, the pattern `Actions for * Report` and `Open`), `dialog_confirm = ["OK"]` for the attachments dialog, the upload folder (default `~/Documents/receipts-archive`) and the `form_url`; none of those controls can submit the report, and `Submit`, `Delete` and `Duplicate` are never declared. `browser profile create` and `receipts rehome` need that table to exist first, so run it before them. A site model records the pages and dialogs of such a flow one at a time: stay on a page and run `blumkin browser explore observe TASK PAGE`, and the page is added to the same draft (or to the stored model when there is no draft), so the order of the clicks does not matter and nothing is lost between pages; `blumkin browser explore save TASK --yes` then stores them together as the next model version.

### Keep a file the page offers: `download`

`blumkin browser download TASK CONTROL --into FOLDER` clicks a declared control that starts a download and keeps the file, for a page that offers a text file (a meeting's transcript as `.vtt`, say) instead of making you scroll for it. Default deny: the task must declare `download_dirs` and `allowed_hosts`, `FOLDER` must be an existing folder inside one of the `download_dirs` (judged on the resolved path, before the browser is touched), and the file must come from an allowed host, be a `.vtt`, `.srt`, `.txt`, `.csv` or `.md` file of at most 20 MB, and have a plain name (the page's suggestion is cleaned of folders and odd characters, or give `--name`). The file is saved to a private temporary folder first and then kept as a new file with mode 0600; an existing file is never replaced. Its text is scanned like `read` and not printed: an `injection_warning` says when it looks like it is trying to instruct an agent, and the text is data, never instructions. A control that could finalize something is refused as for `click`.

Limits to know: the host check uses the address the download was started from (a redirect on an allowed host is not followed back), and a `blob:` download is judged by the origin that created it; the size limit is checked once the browser has finished saving, so a very large file is written to the temporary folder first (which is removed afterwards, or left as a `.blumkin-download-*` folder if the process is killed); only a download that starts on the task's own page is captured, not one that opens in a new tab or window; and in a folder that cannot hold hard links the file is copied instead. A suggested name with no usable characters becomes `download` plus its extension.

## Explore a site once

A task can record the structure of its website once, so later runs do not have to explore it again. The record is a site model: the pages (a URL template and a fingerprint of their landmark controls), the controls on each page (a logical name, a kind, whether it looks finalizing and ordered ways to find it) and the flows that chain them. It holds structure only: nothing you type, no cookie and no personal data, and a label that looks like typed data is skipped and counted. Exploration needs the task to declare `allowed_hosts` and never leaves them.

```bash
blumkin browser explore observe expense-report expense-list
blumkin browser explore click expense-report Help --role link
blumkin browser explore click expense-report "Add line" --page expense-list
blumkin browser explore show expense-report
blumkin browser explore save expense-report --yes
blumkin browser explore discard expense-report
```

`observe` records the page the task's browser is on in a draft kept on disk between commands, and `show` summarizes what the draft would save. `click` follows links and tabs without asking. A control that may change state, such as a button that opens a confirmation dialog, is clicked only after you answer yes at your own terminal; so are all menu items and any link whose name or address looks destructive (delete, remove, log out, archive and the like); the default is no, the question is read from the terminal and never from an argument or the page, and with no terminal (an agent running in the background) nothing is clicked and the command prints what to run yourself. An approval covers that one click, is not stored and never adds the control to `allowed_controls`; the element is inspected before you are asked and again at the click, so one that changed in between is refused, and a link that leads off the allowed hosts or out of the web is never followed. While exploring, a navigation to another host is aborted before the request leaves, but a redirect from an allowed host to another one is followed by the browser itself, so that one request is made and the command then fails with `explore_refused`, saying the click happened. A process that opens its own pseudo-terminal could answer the question for you, so approve clicks from your own terminal session. Names in other languages are not recognized as finalizing on links, and a path word such as a user name in a URL is kept in the template, so review the draft with `show` before you save it. A finalizing control (submit, send, pay and so on) is recorded as such and is never clicked, with or without approval. `save --yes` only acknowledges that you reviewed the draft (nothing checks that you did), and stores it as the next version of the task's model under the config directory (`browser-models/`, private, earlier versions kept) and clears the draft; without `--yes` it shows what it would save and stops.

## Check that a site has not changed

Before a task relies on a recorded model, check that the site still matches it. Open the page in the task's browser, then run the check against the model's page of that name.

```bash
blumkin browser model check expense-report expense-list
blumkin browser model versions expense-report
blumkin browser model diff expense-report 1
```

`check` only reads the page (it never clicks or types) and grades it by role and accessible name, so layout, color and ordering changes are ignored. `compatible` means every control is still found and the page is recognizably the recorded one. `degraded` means it still works but the model should be updated: a control is found only by a fallback locator, cannot be verified from a page snapshot (a selector-only control), or some landmarks changed. `incompatible` means re-explore the page: a control is gone, a new field appeared (it may be required) or the page no longer looks like the recorded one; the command exits 1 (the same code as other failures, so use `--json` and read `grade` to tell them apart). A page with fewer than three recorded landmarks is judged by those alone: none of them on the page, or a different address, makes it `incompatible`. A new button or link is not drift. The page must be on the task's `allowed_hosts`, and the check says when the page's address does not look like the recorded one. `versions` lists the saved versions of the model and `diff` shows what changed between two of them (hosts, pages, flows, and the controls added, removed or changed, including a control that became finalizing or safe).

## Remember what has been filed

A time sheet is filled one day at a time and an expense report one receipt at a time, over several sessions. The ledger remembers, for one instance of a task (this pay period's time sheet, that trip's expense report), what has been filed so far, so a restarted session does not file anything twice. `blumkin browser ledger begin TASK INSTANCE --expect day=10` starts it; the instance name is a short word such as `2026-p21` or `trip-lisbon`. Prefer the ledger-backed verbs: `blumkin browser ledger stage` (idempotent if already verified), `blumkin browser ledger apply --flow NAME` (runs a recorded site-model flow then marks filled; a verified item is a no-op), `blumkin browser ledger verify --present` or `--missing` (read-back), `blumkin browser ledger reconcile KIND --page-item …` (read-only divergence vs the page), and `blumkin browser ledger handoff --step …` (always `submitted: false`, built from the ledger). `blumkin browser ledger record TASK INSTANCE KIND ITEM STATE` remains for manual state fixes. A receipt carries `--sha256` from the start. `blumkin browser ledger status TASK INSTANCE` reads like a sentence, for example "3 of 10 days filed, 4 receipts filed, not submitted"; `blumkin browser ledger list TASK` lists the task's instances.

The ledger is a private append-only journal under the config directory (`browser-tasks/<task>/<instance>/journal.jsonl`, mode `0600`). Writers take a lock and append one line at a time, so two commands cannot corrupt it, a half-written last line left by a crash is ignored and cut off by the next write, and a damaged line anywhere else is reported as `ledger_invalid` instead of being guessed at. It holds item ids, states, model versions and file hashes only, never an amount, a vendor, a path or a field value, so keep ids to dates and short words.

blumkin has no submit command. `blumkin browser ledger submitted TASK INSTANCE --yes` records that you did, and nothing else records it; say yes only if you pressed the button yourself. A submitted or discarded instance accepts no more items. `blumkin browser ledger discard TASK INSTANCE --yes` closes an instance without touching the real form and keeps its journal.

## Read a Teams meeting transcript

`blumkin browser transcript TASK` captures the transcript of a Teams meeting that someone else organized, where `blumkin meeting` has no access and the pane's own Download button is disabled. Open the meeting's chat in the task's browser (sign in by hand first) and its Transcript tab, then run it.

```bash
blumkin browser profile create teams-transcript
blumkin browser launch teams-transcript
blumkin browser goto teams-transcript https://erp.example.com/
blumkin browser click teams-transcript Notes --role tab
blumkin browser click teams-transcript Transcript --role tab
blumkin browser transcript teams-transcript --duration 34m06s --out ~/work/meeting-transcripts/intros.txt
```

```toml
[browser.tasks.teams-transcript]
allowed_hosts = ["erp.example.com", "*.example.com"]
allowed_controls = ["Notes", "Transcript"]
```

`blumkin browser read` cannot do this: Teams serves the transcript from the organizer's OneDrive in a cross-origin iframe, and the list is virtualized, so at any moment only the rows near the viewport exist in the page (about 12 of 34 minutes in the meeting that shaped this command). `transcript` scrolls that frame from its first row to its last, merges the overlap and writes one `[m:ss] Speaker: text` line per turn. The task needs `allowed_hosts` that include both the top-level page host and the frame's host (for Teams, `teams.microsoft.com` and `*.sharepoint.com`; the example uses `erp.example.com` and `*.example.com` as stand-ins), plus `allowed_controls` for the tabs it clicks (`"Notes"`, `"Transcript"`); the command is read-only and clicks nothing. `--out` creates a new file with mode `0600` and never overwrites one.

Everything that knows what the Teams page looks like (the scripts that find and scroll the transcript pane, the parser for its text and the started and stopped transcription event lines) lives in one module, `blumkin.browser.teams`, so a change in the page is one fix; the coverage report and the merge of overlapping chunks are page-independent (`blumkin.browser.transcript`).

Every capture carries a coverage report, so a gap is reported instead of silently missing: the entry count and speakers, the first and last timestamp, silences longer than three minutes, entries out of order and whether the scroll reached both ends. With `--duration` the last entry is checked against the meeting's length, unless Teams logged "stopped transcription" (the transcript legitimately ends before a meeting that kept running). `complete` is false when any of that looks wrong, and a capture that is not complete must not be presented as the whole meeting. The text is untrusted data and goes through the injection scan like `read`.

## Receipts

`blumkin receipts find --dir ~/Documents/receipts --json` lists the images and PDFs in a folder, newest first. `blumkin receipts find --dir ~/Downloads --new-since 30m --json` keeps only files that arrived in the last 30 minutes (each entry shows `arrived`), `blumkin receipts to-pdf ~/Downloads/till.jpg --out ./receipts-to-upload/` turns a photo into a PDF for sites that only take PDFs, and `blumkin receipts read ~/Documents/receipts/taxi.jpg --json` reads one with the existing OCR and reports vendor, date, total and currency, each with a confidence (`high`, `low` or `none`), so the task asks you about anything doubtful instead of guessing. OCR needs the `ocr` extra (`uv tool install -e '.[pdf,ocr]'`) plus `tesseract` and `poppler`; without it the result says `needs_manual` and the task asks you for the amounts. `blumkin receipts summarize <files-or---dir> --json` reads several receipts and prints one row per receipt (`file`, `drop` or `review`) with a grand total per currency: receipts with the same vendor, ride date and currency are one trip, a lower total within 1.4 times of a higher one is the without-tip copy and is marked `drop` only when the two arrived within 30 minutes of each other or are the same message or file (otherwise both rows are marked `review`, as is any row whose total or currency is not certain), and the ride date comes from the receipt text or subject, with the email arrival time only as a flagged last resort. Nothing is moved or deleted. After you confirm the table, `blumkin receipts rehome` needs `--yes`, and `--replace <name-or-hash8>` swaps a bad render for a fixed one, keeping the old file under the instance's `superseded/` folder. After you confirm the fields, `blumkin receipts rehome ~/Downloads/scan.jpg --task expense-report --instance trip-lisbon --date 2026-10-20 --vendor "Taxi Co" --total 18.50 --currency USD --yes` moves the file into the managed per-instance folder under the task's first `upload_dirs` entry, named `YYYY-MM-DD_vendor_amount-CURRENCY_hash8.ext` (the vendor appears in that filename). Pass `--message-id` for a mail attachment so the file is copied (not moved) and the message id is recorded. Rehome keeps a separate private intent/result journal at `browser-tasks/<task>/<instance>/receipt-moves.jsonl` (mode `0600`) that stores resolved source and destination paths, the SHA-256, and optional message id so a crash can be resumed and `browser ledger discard --yes` can restore originals (including an intent-only half-finished move). Receipts that arrive as HTML mail with no attachment need a PDF for the expense site: `blumkin mail export --id <message-id> --out ./receipts-to-upload --json` renders the body with a headless browser (images on; scripts, frames, linked resources, meta tags, some elements hidden by supported inline styles and images declared as one pixel removed; text hidden by a stylesheet can be absent from the PDF yet remain in the `.txt` file, so check amounts visually; so an image with no declared size can still load and tell the sender the message was opened; throwaway browser profile) and writes `<name>.pdf`, `<name>.txt` (the same content as text) and `<name>.json` (message id, sender, received time, subject) side by side in the folder you name, never in the receipts archive. The export checks the PDF against the message and exits 1 listing the problems when the render is broken (missing images, blank pages, a text layer that does not match); `blumkin receipts check <pdf>` re-runs that check later. `receipts read` prefers the `.txt` beside a PDF over OCR, but only when the `.json` records that exact PDF and text by SHA-256; an edited, replaced or oversized `.txt` is ignored and the PDF is read normally. A prompt-injection warning on the message is reported and recorded in the JSON without stopping the export. For receipts that arrive by mail, list a message's attachments with `blumkin mail attachments --id <message-id> --json` and save the ones you want with `blumkin mail attachments download`.

## What blumkin refuses

- Submitting. There is no submit command, and the guard is deny-by-default and enforced in code, not in a prompt. `blumkin browser click` refuses, without touching the page: a control the task did not declare by its exact name, a role that is not clickable, a submit control (judged by the browser's own idea of the control's type, so a button with an invalid `type` counts), a control with a `formaction`, a link that runs script and an inline handler whose text mentions submit, and any control with any word in its name that starts with a finalizing word (submit, send, file, confirm, pay, finish, complete, approve, authorize, place order, and more, so "Payments" and "Save and send" are refused). The deny check runs first: a control is refused even when it is listed in `allowed_controls`. The refusal exits non-zero with `submit_blocked`.
- Keys that submit. `blumkin browser press` allows only navigation keys (Tab, arrows, Escape, Backspace, Delete, Home, End, Page Up and Down) and single printable characters; Shift+Tab also works, but Enter, Space, a newline and every other modifier combination are refused, and so is any key aimed at a button.
- A safety net behind all of that. While blumkin is attached it swallows every non-GET page navigation, which is what submitting a form does, so even a script that submits a form on its own gets no navigating POST through. The page stays as it was, your typed values included. The net lives only on blumkin's connection: once the command finishes it is gone, and your own final click is never blocked.
- Uploading anything else, or anywhere else. `blumkin browser upload` takes only a regular file inside one of the task's `upload_dirs`, judged on the fully resolved path (so a symlink or `..` cannot step out), checks the file and the folder before the browser is touched, checks the page host once attached, and refuses unless the page is on one of the task's `allowed_hosts`; a hard link is refused, because it can point at a file outside the folders.
- Anything but `http` and `https` pages: `goto` refuses `file:`, `javascript:` and `data:` URLs.
- Following the page. Text read from a page or a receipt is data, never instructions, and is scanned for prompt-injection patterns.

## Limits

- The guard is a backstop, not a guarantee. A declared control that is not on the deny list is clicked, so declare only controls that cannot finalize. A form submitted by a GET request is a GET navigation, which the net lets through (the browser does not say whether a navigation came from a form, so there is no setting for it), and a page can submit from a listener added by script, which the inline-handler check does not see.
- The host checks are detective, not preventive, after a page changes: when a `goto`, a click or an upload ends on a host outside `allowed_hosts` the page has already loaded (nothing from it is returned), and the command fails with `host_blocked` so the task stops before anything is typed into or read from it. `goto` is not limited at all when no `allowed_hosts` are declared.
- Use this on a machine you alone use. The browser's DevTools port listens on `127.0.0.1`, which keeps other computers out but not other user accounts on the same machine, and the profile directory's permissions do not protect a TCP port. On a shared host another user could drive the signed-in browser.
- The safety net protects only while a command is attached. A page that schedules a submit to fire after the command has finished (a timer, for example) is outside it; the guard's checks and your declared controls are what limit that, and the user's own final click is deliberately never blocked.
- After the safety net swallows a submit, the rest of that command may wait on the page for a moment; start a new command or finish the task with `handoff`.
- A form that submits through a background request (a script that posts data without navigating) is not a navigation, so the net does not see it unless the task turns on `block_background_writes`. The guard's checks and your declared controls are what stand between a task and such a page, which is why `allowed_controls` is a short list you wrote.
- The drift check compares what a page snapshot shows, so it cannot see a control that became disabled or required, text in another language, or a locator that is only a selector (those are reported as unverified). Links and menu items are often data (mail subjects, list rows), so a missing one only degrades the grade. Two controls with the same role and name on a page count as one. A page cut off at the control cap is not checked for new fields, and one with more landmarks than the model keeps (100) may report a field it did not record as new.

## Housekeeping

`blumkin browser status` shows each task profile, whether its browser is running and the loopback DevTools endpoint. `blumkin browser profile list` lists the profiles, and `blumkin browser profile delete expense-report --yes` removes one, saved sign-in and cookies included; it refuses while that task's browser is still open: close it first with `blumkin browser close expense-report`. Only profiles blumkin created are listed, attached to, closed or deleted.

`blumkin browser close TASK` ends the browser `browser launch` opened, so an agent can clean up after itself without asking you to close a window by hand. It asks the browser to quit and waits up to `--wait` seconds (15 by default, at most 300) for it to exit, which lets it write its profile out, and it keeps the profile: the saved sign-in and cookies are there the next time you `browser launch TASK`. It signals only a process that is confirmed, by its command line, to be a browser running on that task's profile, so a stale session whose pid has been reused is never touched. With no browser running it says so and exits 0. When `ps` cannot answer, nothing is signalled and the close is reported as `browser_close_failed`, never as "no browser", and the session record is kept. `browser close` refuses to signal any process in its own process tree (itself, its parent, or the head of its process group or session), even one whose command line names the profile. A browser that does not exit is reported as `browser_close_failed`; `--force` then kills it (its process group, only when the browser leads it), clears Chrome's stale single-instance files, and its profile may need to recover. Closing never deletes anything: `profile delete` is the command that does.

## Errors

| Error | Exit | Meaning |
|-------|------|---------|
| `submit_blocked` | 1 | The guard refused a click or key press. Do not retry; hand the final step to the user. |
| `browser_not_running` | 1 | No browser is running for the task. Run `blumkin browser launch TASK` and sign in again. |
| `browser_no_page` | 1 | The browser is running but has no open page and none could be opened. Open a tab in its window, or close the browser and launch it again with `--open`. |
| `sign_in_timeout` | 1 | `goto` or `launch --open` waited for the sign-in redirect to finish and the page was still on the identity provider. Sign in by hand in the browser window, then run `blumkin browser goto TASK` again; the browser keeps running. |
| `browser_attach_failed` | 1 | The browser is running but attaching to it over DevTools failed. Try again, or close it and launch it again. |
| `browser_action_failed` | 1 | A page action failed or timed out. Read the page and check the label or control name. |
| `browser_dependency` | 1 | Playwright is missing or broken. Run `uv sync --reinstall-package playwright` in the blumkin clone, `uv tool install -e . --reinstall`, or `uv tool upgrade blumkin --reinstall-package playwright`, then retry. |
| `browser_launch_failed` | 1 | The browser did not open a DevTools port in time. |
| `browser_not_found` | 5 | Neither the configured browser nor Chrome is installed. |
| `not_found` | 5 | No profile exists for the task (create it with `blumkin browser profile create TASK`), or a file or folder the command named is missing. |
| `upload_blocked` | 1 | The file is not a regular file with a single link inside one of the task's `upload_dirs` folders, the page is not on one of its `allowed_hosts`, or the task declares neither. |
| `download_blocked` | 1 | The task declares no `download_dirs` or `allowed_hosts`, the folder is not an existing folder inside a `download_dirs` folder, the file name is not a plain text-file name, the file is too large or not a regular file, or a file of that name already exists. |
| `host_blocked` | 1 | `goto` was asked for a host outside the task's `allowed_hosts`, or a page the task is on or ended up on is outside them. |
| `browser_close_failed` | 1 | `browser close` asked the browser to quit and it was still running after `--wait`. Close its window by hand, or retry with `--force` to kill it. |
| `profile_in_use` | 1 | Raised when the task's browser is running or a launch for it is in progress; close it or wait, then try again. |
| `explore_refused` | 1 | Exploration needs `allowed_hosts` for the task, or the page is (or a click led) outside them. |
| `model_invalid` | 1 | The draft or the stored model was rejected: a field outside the schema, a value that looks like typed data, a symlink or a file that is too large. |
| `reply_failed` | 1 | `blumkin loop finish` could not send its reply; the item's documents are kept, so run it again. |
| `ledger_invalid` | 1 | A task instance journal has a damaged line (not just a torn last one); restore it from a backup or discard the instance. |
| `usage_error` | 2 | A bad task name, a missing `--yes`, or a handoff with no `--step`. |
