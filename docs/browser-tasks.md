# Browser-assisted tasks

Some chores have no API: filing an expense report, filling in a weekly time sheet. blumkin handles them by driving a browser **you** sign in to, filling in the form for you and then stopping. blumkin has no submit command, and a browser task ends by telling you exactly what to review and which button to press. The guard blocks the listed submit paths; the Limits section lists the cases it does not block.

## How it works

1. You create a dedicated browser profile for the task and launch it. You sign in by hand, SSO and MFA included. If your task definition authorizes it, an agent may click one thing for you on the identity provider's account picker: the tile of the one account the task names, with the sign-in host and that tile added to the task's policy only for that click and removed right after; it never types a username and hands any password, MFA or consent prompt back to you. blumkin never sees, types or stores your credentials; the session cookies live only in that profile directory.
2. An agent (or you) runs the task's skill, which attaches to that browser over the Chrome DevTools Protocol (CDP) with [Playwright](https://playwright.dev/python/), reads the page, fills in fields and uploads files.
3. The task ends with a handoff: what was filled in, what still needs your decision, and numbered steps for the final click. The result always says `submitted: false`.

Chrome, Edge and Chromium are supported. blumkin uses the browser already installed on your machine and never downloads one.

## Set up a task

Create the task's profile and tell blumkin which controls it may click.

```bash
blumkin browser profile create expense-report
```

Then add the task's policy to `~/.config/blumkin/config.toml`.

```toml
[browser]
default = "edge"          # chrome | edge | chromium; Chrome is used when unset or not installed

[browser.tasks.expense-report]
allowed_controls = ["Add line", "Create report"]   # exact names the form shows; `*` stands for any text
allow_all_controls = false                         # optional; true = deny-list mode (see below)
extra_deny_names = ["release"]                     # optional; adds to the built-in list
draft_controls = ["Calculate"]                    # optional; submit-type buttons you verified only recalculate
dialog_confirm = ["OK"]                            # optional; confirm buttons that are valid only inside a dialog
dialog_landmarks = ["Add", "Delete"]                # optional; controls that together mark a popup the page does not flag as a dialog
form_url = "https://erp.example.com/expenses"      # optional; what `goto` and `launch --open` open
sign_in_hosts = ["sso.example.com"]                # optional; extra identity-provider hosts `goto` waits through
sign_in_account = false                            # optional; true lets `browser sign-in` pick the profile's account
upload_dirs = ["~/Documents/receipts"]             # folders `upload` may read from; none = no uploads
download_dirs = ["~/transcripts"]                  # folders `download` may save into; none = no downloads
allowed_hosts = ["erp.example.com"]                # sites `upload` may send to; also limits `goto`
block_background_writes = false                    # optional strict mode, off by default; see below
use_profile_address = false                        # optional; true lets `browser address` print the profile's address
```

The `[browser]` and `[browser.tasks.*]` tables go anywhere in `config.toml`, next to your `[profiles.*]` tables. If every command instead fails with `named [profiles.*] layout cannot mix top-level flat keys (browser)` although the file is valid TOML, your blumkin build predates that support (release 1.13.0 is such a build, and so are the `[loop]` and `[cron]` tables on it): check `blumkin --version`. `blumkin upgrade` fixes it once a release newer than 1.13.0 is published; until a release newer than 1.13.0 is published, run the checkout with the dev launcher (`scripts/dev/blumkin`, see the `blumkin-dev` skill) or wait for that release.

`allowed_controls` is what makes `blumkin browser click` work for the task: a control that is not listed is refused, and the refusal lists the names and patterns the task does declare. A name may contain `*` for any text, so one entry such as `"Actions for * Report"` covers a control whose name carries the trip's own name (a saved report's actions link), with no config edit per trip. A pattern must start with fixed text (no leading `*`), hold at most two `*` (only an ASCII `*` is a wildcard) and keep at least four letters or digits of fixed text, and that fixed text cannot be a finalizing word (`"Submit *"` is refused when the task is used). The name actually clicked is still checked against the built-in finalizing words (submit, send, pay, confirm, file, complete, finish, approve, ...), so a pattern never reaches those; names such as `Delete` or `Duplicate` are not on that list, so they stay out of reach only because a menu item is declared one by one, exactly (`Open` yes, `Delete` no): keep the fixed text of a pattern specific, and add such words to `extra_deny_names` if a page could show them in a name your pattern would match. Everything else about a matched control is unchanged: it is vetted like any other, and a duplicate name still needs `--nth`. `extra_deny_names` can only add to the built-in list of finalizing words, never shorten it. `dialog_confirm` lists exact names of buttons that confirm a dialog's own rows (an attachments dialog's `OK`, which is usually a submit-type button and would otherwise be refused as a submit control): such a button may be clicked only when it sits inside a dialog (`<dialog>`, `role=dialog` or `alertdialog`) whose form, if it has one, lies inside that same dialog, so a dialog nested in the report's own form never qualifies, and a dialog that also holds a finalizing control (a modal wrapped around the whole report and its own `Submit`) never qualifies either; `OK` itself is not on the built-in list of finalizing words, it is refused only because it is usually a submit-type button, and a page that marks a wrapper as a dialog is judged by what that dialog holds; the same name anywhere else is refused, and a name that is a finalizing action (`Submit`, `Pay`, `Send`, `Confirm`, ...) can never be listed, so the report's own `Submit` stays out of reach. A formaction override, a script link or a submitting click handler is still refused on it. A dialog confirm needs no entry in `allowed_controls`. `dialog_landmarks` is for a popup the page does not mark as a dialog (Oracle ADF renders the Manage Attachments popup without `role=dialog`, so a declared `OK` was refused as not in a dialog): list at least two exact control names that sit in that popup's toolbar (`"Add"`, `"Delete"`), and the smallest container around the `dialog_confirm` button that holds a control of each name is judged as a dialog, by what it holds. The same checks apply as for a real dialog: a container that also holds a finalizing control (the report's own `Submit`, so the whole page in a wrapper) never qualifies, nor does one with more controls than can be checked, and a submit-type button in a popup that sits inside the report's own form is still refused; only a button that cannot submit anything (a link or a `role=button` element) is spared the form check. Names must be distinct (`Add` and `add` count as one), without `*`, not finalizing, and the key needs `dialog_confirm` beside it, so one common word cannot mark a whole page. The page is searched for a button or link whose visible text, label, value or title is the name, ignoring case, and the page supplies that evidence: like any declared button, the confirm is not proof that a script-installed listener does not submit, which `block_form_submission` and the held-controls scan are there to catch. `blumkin browser init-task --template expense-report` writes `dialog_landmarks = ["Add", "Delete"]`. `upload_dirs` is where the task may upload files from (absolute folders, or folders starting with `~/`, but never `/`, the whole home directory or a path that climbs out of it; `~user` paths are refused) and `allowed_hosts` is where it may send them (`erp.example.com`, or `*.example.com` for any subdomain, which needs a dot after the star, though public suffixes such as `co.uk` are not checked); with either missing `blumkin browser upload` refuses every file, so a page cannot make an agent upload an arbitrary file such as a key or a token, or send a receipt to another site. `download_dirs` is the same for `blumkin browser download`: where a file the page offers may be saved (default deny). Once a task declares hosts, `blumkin browser goto` refuses any other host too and every other command refuses to act on a page outside them; with no `allowed_hosts`, `goto` is not limited at all, so declare them. An unknown key in a task table is an error, so a typo such as `allowed_control` does not silently leave the task with an empty allow list. Everything that belongs to you personally (the form URL, your receipts folder, your categories, your default weekly hours) lives in your own task definition, not in blumkin; see [`operator-config.md`](./operator-config.md).

`allow_all_controls = true` opens up navigation for a task without listing every control: any link, tab, tree item, option or checkbox may then be clicked without being declared in `allowed_controls` (a saved item's date link, a row's expander), and everything that refuses a click still applies: the built-in finalizing words (submit, send, pay, confirm, file, ...), the task's `extra_deny_names`, and the check of the element itself (a submit-type control, a form-action override, a script link or a submitting click handler is refused). A name with the word `delete`, `discard`, `duplicate`, `remove` or `void` in it is refused unless `allowed_controls` declares it (a name or a pattern you wrote); add any other destructive name you can think of to `extra_deny_names` (for example `"reject"`, `"reset"`), since only these few are built in. A **button is never opened up**, and an element that is a `<button>` or a button-type `<input>` counts as one whatever ARIA role the page gives it (a tab or link drawn as a button still has to be declared): Save, Save and Close, Calculate, Create Item and every other button must still be declared in `allowed_controls`, by name or by a pattern you wrote, because a handler a script installed on a button can send a background request that saves or sends the form, and blumkin cannot see it from the page; a menu item must be declared by its exact name, and a pattern never reaches one (so a row menu's `Delete` or `Duplicate` stays out of reach), and `blumkin browser download` and the tabs a flow switches through must be declared too. `dialog_confirm` and `draft_controls` are unchanged. **What this mode trusts:** a link, tab or option with a script-installed listener can also send a background request, and blumkin cannot inspect listeners any more than for a link you declared by name; the difference is that with this mode you did not look at each one first. Block that class of request with `block_background_writes = true` where the page allows it (Oracle's pages do not), and list anything you do not want clicked in `extra_deny_names`. The default is off, so a task is deny-by-default until you opt in; use it for a form whose links change from trip to trip, and keep declaring every button.

`sign_in_account` lets `blumkin browser sign-in TASK` pick the profile's own account on an identity provider's account picker, after `browser goto` was redirected to one, so the sign-in does not wait for you to click your own tile. It is off by default and needs the task to declare `allowed_hosts` and the profile to record its account address (`profiles set-email`). It never types a credential. It looks at the page and clicks only when all of these hold: the page is https on a sign-in host (the built-in ones and the task's `sign_in_hosts`) that is not one of the task's own `allowed_hosts`; it shows no field to type into (a password, a code); and exactly one tile is for the account. A tile is the button or link (a marked child counts as the nearest one around it) whose names - its text, labels, titles and the labels it refers to - hold the address as a whole word (a neighbouring letter, symbol or accent makes it a different address, and ASCII case aside there is no look-alike), that names no other address, that carries none of the words remove, forget, sign out, log out, delete, allow, authorize, grant, consent, accept, approve, revoke, send, code, confirm, verify, password, create, add, another, different, other, continue or next, and that links nowhere off the sign-in hosts. A page with any visible text box, text area, editable region or menu to type into is refused. The profile's address must be one plain address (a name, an at sign, a dotted domain); anything else is refused without being shown. Anything else is refused and nothing is clicked: another site or an `http` page, no tile, several tiles, or a page with a field to type into. The tile's names also go through the same finalizing-name check as any click (submit, send, pay, the task's `extra_deny_names`), so a tile named like one is refused. The page is judged in one evaluation, then the chosen element is judged again and clicked in a single step on the page, and the click happens only if it is the same element with the same names, so a tile changed in between is not clicked. After the click it checks that the page is still on a task or sign-in host, and reports a handover when a password, a code or consent follows. It adds no host or control to the task and writes nothing to `config.toml`, so there is nothing to clean up if it is interrupted; the only temporary thing is the sign-in allowance for the safety net while the click runs, which is released even when the command is interrupted, and which lets requests from a sign-in page through (so a tile that posts to another host is only caught by the check afterwards). The result shows the account masked (only its first letter and its domain). It was written against the common picker shapes and checked with test pages, not against every provider's real page, so a page it does not recognize is refused, not guessed at.

`draft_controls` is for a button that only recalculates what is on the page, such as the `Calculate` button of a mileage form, which the page renders as a submit-type control inside the report's own form (so the guard refuses it even when it is listed in `allowed_controls`). Declare it by its exact name after checking by hand that clicking it recalculates and does not save or send the report. A declared button is spared the submit-control check and nothing else: a name that is a finalizing word (`Submit`, `Pay`, ...) or holds a `*` is refused when the task is used, a button with a formaction override, a link that runs script or a click handler that submits is still refused, it cannot start a download, and the form-submission safety net stays on. Two more conditions guard against a page that renames its real Submit: the declared name must belong to an actual button (not a link, an image input or another element), and none of the other names that button goes by (its text, value, title, id or the labels of what it holds) may be a finalizing word. What the guard cannot see is what the click does: the safety net swallows an ordinary form post (a navigation), but not a background request (`fetch` or `XMLHttpRequest`, which is how many sites, Oracle's among them, both recalculate and save), `block_background_writes` would swallow those too but also breaks a real recalculation, and a click handler added by script is invisible to blumkin. So the declaration is yours: declare a name only after checking by hand that the button recalculates and does not save, and when in doubt leave it out and click the button yourself.

`block_background_writes` is an opt-in strict mode for simple forms, off by default. While a command is attached, the safety net then also answers every other write (`fetch`, `XMLHttpRequest`, a beacon) with an empty response, so a handler on a control you declared cannot post form data in the background; the server never receives it. It breaks pages that need background writes to work: an ERP page that sends almost every interaction, including adding a line, as a background POST will appear to do nothing, so leave it off for those. There is no matching setting for GET form submissions: the browser does not expose whether a navigation came from a form or from a link, so blumkin cannot tell a form GET from a link with a query string, and blocking every navigation with a query string would break ordinary browsing. Strict mode covers requests the page makes while blumkin is attached; a request a service worker makes itself is routed, but a page request that a service worker answers is not seen by the route, and neither are WebSocket messages or hyperlink pings, so "every write" here means every HTTP write the browser lets blumkin route.

`use_profile_address` lets a task read the operator's physical address, for a form that asks for one (a mileage expense, say). It is off by default and the address is optional: `blumkin --profile NAME profiles set-address` stores it on a profile (it asks at a hidden prompt, or takes `--stdin`, so it stays out of shell history; `--clear` removes it) and never prints it back. It is left out of `profiles list` (which only says whether one exists), `doctor`, errors and the profile's printed settings. A task whose table sets `use_profile_address = true` can then run `blumkin browser address TASK` (with `--profile NAME` before `browser` to pick the profile) to get it; any other task, or an unknown one, is refused before the address is looked at. The command only returns the address: it reaches a site only when you or the agent fill it in with `browser fill`, on a host the task allows. The address is kept in `config.toml` next to the rest of the profile, in plain text, and `set-address` tightens that file to your user only. `use_profile_address` is a guard rail for the commands, not a boundary against someone who can already read or edit `config.toml`: they can read the address, or authorize a task, without blumkin at all.

### Telling which window an agent is driving

Each task has its own colour, derived from the task name (`colour` in `blumkin browser status`, `launch` and `endpoint`, always the same for a task). Whenever blumkin attaches, the page it is on shows a small `blumkin - TASK` pill in the bottom left corner in that colour, with a thin line of it along the top edge, so the window an agent is driving is recognizable at a glance. The mark takes no clicks, is hidden from the page text and the accessibility tree that `browser read` returns, is added through the browser's style API so a page's content security policy does not block it, and is only added to a page on an allowed host (never to a sign-in page or a blocked one; the page's own address is checked in the same step that adds it). The `explore` and `model check` commands show it too. The colour is dark enough for the white text to meet the 4.5:1 contrast of WCAG AA. It stays until the page navigates and is put back by the next command; closing the browser closes the window and the mark with it. Commands attach one at a time and detach in between, so the mark is not removed on each detach: it belongs to the window for as long as the window lives.

### Signing in, the first page and the endpoint

`blumkin browser launch TASK --open` starts the browser and opens the task's `form_url` in one step (any other address goes through `blumkin browser goto TASK URL`). A site that sends the page to an identity provider (login.microsoftonline.com, login.microsoft.com, login.live.com, accounts.google.com, or a host in the task's `sign_in_hosts`: an Okta, Auth0, OneLogin or Ping tenant is named there, for example `acme.okta.com`, because anyone can register such a tenant) is waited through by `launch --open` and by `blumkin browser goto TASK [URL]`: only the page address is polled, for up to `--sign-in-wait` seconds (default 120, `0` to not wait), while you sign in by hand, nothing is ever done on the sign-in page, and the command carries on as soon as the page is on an `allowed_hosts` host, so nobody has to say they are signed in. If the time runs out on the sign-in page (`sign_in_timeout`), sign in and run `goto` again; the result names the host that was waited on (`sign_in_host`) and how long (`waited_for_sign_in_s`). A `form_url` must be an https address on one of the task's `allowed_hosts`. `blumkin browser status` shows how many pages the browser has open: a browser with no open page is running but cannot be driven, so the status says so, and the next browser command opens a blank page for you (`browser_no_page` says what to do when that fails, `browser_attach_failed` when the attach itself fails, `browser_not_running` when nothing was launched). A task browser is usually ended by closing it from the terminal (or killing it), which Chrome and Edge record as a crashed session and answer on the next launch with a "Restore pages?" bubble that can cover the page you sign in on. `launch` starts the browser with `--hide-crash-restore-bubble` and first marks the profile's last exit as clean (`exit_type` and `exited_cleanly` in the profile's own `Default/Preferences`, nothing else in that file, and only for a profile blumkin created), so the bubble does not appear. The DevTools port changes on every launch: `blumkin browser endpoint TASK` prints it, and `status --json` carries it too. After `blumkin browser close` and a new launch the identity provider's session cookies may be gone: cookies it sets without an expiry (session cookies) are dropped when the browser closes, so you may have to sign in again, and keeping the browser open between runs is what keeps the sign-in. A site that sets persistent cookies keeps the session in the task profile across launches.

## Run a task

Launch the browser, sign in by hand in the window that opens, then let the skill drive it.

```bash
blumkin browser launch expense-report
blumkin browser goto expense-report https://erp.example.com/expenses
blumkin browser read expense-report
blumkin browser fill expense-report "Amount" "12.50"
blumkin browser upload expense-report "Receipt" ~/Documents/receipts/taxi.jpg
blumkin browser select expense-report "Type" "Taxi"
blumkin browser verify expense-report "Amount" "12.50"
blumkin browser click expense-report "Add line"
blumkin browser handoff expense-report --filled "1 line, 12.50 USD" --step "Review the line and the total." --step "Press Submit at the bottom right."
```

Each command attaches to the running browser, does one thing and detaches; the browser stays open with your session. `blumkin browser click` finds the control by name; pass `--role` (`--role link`, `tab` or `menuitem`) to choose when the name exists in more than one role, for example `blumkin browser click expense-report "Help" --role link`. The two ready-made skills are [`expense-report`](../.agents/skills/expense-report/SKILL.md) and [`time-sheet`](../.agents/skills/time-sheet/SKILL.md).

`blumkin browser click` without `--role` finds the control by its name across the clickable roles and says which role it found; a name that exists in more than one role, or two controls of one name within a role, is refused until you pass `--role` or make the name unique (a second role appearing after the first poll found a match is not seen). When a page legitimately repeats a name (a list that has a "More actions" button on every row), `--nth N` says which one is meant: N is 1-based, in DOM order (the order `browser read --aria` lists them, which can differ from the visual order), and the click is refused with the real count when the page has fewer than N within `--wait`. `--nth` is for `click` only; `browser download` still refuses a repeated name. `--nth` does not change what a task may click: the name must still be declared, a finalizing name is still refused, and the element it picks is vetted before the click. Page order can change between loads, so read the page (`browser read --aria`) before relying on a position, and prefer a unique name when there is one. It waits up to `--wait` seconds for the control: 5 by default when finding it by name, so a missing control fails in seconds, and 30 (the action timeout) when `--role` is given; `--wait` is capped at 300. `blumkin browser refresh-tab TASK TAB --via OTHER` reloads a pane that only reloads when another tab is shown first: both tabs must be declared in `allowed_controls` (checked before the first click), it selects `OTHER`, checks the page is still on an allowed host, then selects `TAB` again; if the second step fails the error says the page was left on `OTHER`. `blumkin browser read TASK --frame N --wait SECONDS` waits for a frame that attaches late (and, for text, for it to have text) instead of reading it empty; a read that fails while the frame is still navigating is retried until the wait is over. A click returns before the page it started has finished, and a read straight after could still show the page that was left (a saved item whose form seemed to be unchanged), so `click` waits for the page to settle before it returns: the network goes idle and the DOM stays unchanged for half a second, in at most four seconds, after a 0.3-second grace for what the click started to begin; neither wait is an error, and an update that arrives later than about a second after the click is not waited for (use `--expect-heading` for that) (a page that keeps polling never goes idle; `settled` is then false). The output says where the page ended: `url` (no query or fragment, a long path segment masked), `heading` (the first visible `h1` to `h3` or `role=heading` element, which is page text and so untrusted: web addresses are removed and it is withheld, as `heading_withheld`, when it reads like an instruction to an agent) and `settled`. `--expect-heading TEXT` also waits up to 15 seconds for a visible heading that contains TEXT (any case, at most 100 characters) and otherwise fails with an error that says the click WAS made, so read the page instead of clicking again; a failed wait never re-clicks. The wait runs on the page the click landed on only after it has been checked against `allowed_hosts`, so a click that leaves the task's hosts shows nothing from the foreign page; a ledger `apply` click step pays the same short wait. `fill`, `select` and `upload` wait the same way after their action and report `settled`, `url` and `heading` (a `--private` upload reports only `settled`); `--no-settle` skips the wait, and a ledger `apply` fill step does not wait, since a fill rarely changes the page. `--expect-heading` is for `click` only.

### Fields the page repeats, dropdowns and frames

`blumkin browser read TASK --aria` summarizes each combobox or listbox that only holds options (`combobox "Expense Type" (27 options, selected "Lodging")`; add `--options` to list them), so a report with many items does not fill the read cap with option lists. `--within ROLE[:NAME]` keeps one subtree of the snapshot, such as `--within dialog` for the open dialog or `--within "dialog:Manage Attachments"`, which shows the dialog's own `OK` and its rows however long the page is; a name that is not found is refused with the names that role does have. `--limit` and `--offset` read a long page in windows: the JSON carries `truncated`, `total_chars` and the `next_offset` to continue from, and the text output says which `--offset` to use. The page is scanned for prompt injection before it is narrowed.

`blumkin browser fill`, `select` and `upload` find a field by its label. When the page repeats a label (a second Date, Type and Amount appears once the report has an item), the command refuses and lists every match with its role and accessible name; narrow it with `--exact` (the whole label), `--role` (look it up by accessible role and name) or `--nth N` (1-based, in DOM order, the order `blumkin browser read TASK --aria` lists them), as `click` does. `blumkin browser select TASK LABEL OPTION` chooses an option in a native dropdown or an ARIA combobox and refuses an option or field named like a finalizing action; a combobox and its option are vetted like a click (a submit control is refused) and `--role` for it is one of combobox, listbox, searchbox or textbox. `--frame N` (a number from `blumkin browser frames TASK`, pinned with `--host`) works inside a child frame such as an attachments dialog, which must be on a host in `allowed_hosts`; uploads there still go only from the task's `upload_dirs`. `fill` and `select` check what the field holds afterwards: `matches` says whether it is exactly what was set, and when it is not (an autocomplete expanded the text to a canonical form, or rewrote it) the field's value is returned as `read_back`; what was set is never echoed back and a password field is never read. A label that some hidden fields also carry (a `Type` next to the `Vehicle Type`, `Fuel Type` and `Flight Type` fields a form shows only for a matching expense type) means the one visible field for `fill` and `select`; with several visible fields the refusal says how many are visible and how many hidden, marks the hidden ones in its list, and `--nth` still counts every match. For a sensitive value (a card or account number), leave the value off `fill` so a hidden prompt asks for it, or pass `--stdin`: it then stays out of shell history and `ps`, and the field's value is never printed (`--no-read-back` does the same for a value given as an argument; `matches` still says whether the field holds it). `blumkin browser verify TASK LABEL` is the read-only check: it compares the field with an expected value (an argument, `--stdin` or a hidden prompt) and prints only `match`, `mismatch`, `missing`, `ambiguous` (narrow it as for `fill`) or `unreadable` (a password, one-time-code or other secret field is never read), never the value, and exits non-zero unless it is a match. To keep a receipt's amount out of command and tool logs, `blumkin receipts rehome` takes the total at a hidden prompt or with `--total-stdin`, and `--private` prints only an opaque `ref` (no path, file name or amount; failures name only their kind). `blumkin browser upload TASK LABEL --receipt-ref REF --instance KEY` then uploads that filed receipt without its path or name appearing on a command line or in the result, which instead says `attached` (whether the page holds the intended file) and `persisted`; `--private` with a path argument only redacts the result and driver errors; the path itself is still on the command line, so use `--receipt-ref` to keep it off. The upload folder, host, regular-file and single-link checks are unchanged, and archive naming and the journal are as before. `blumkin browser press TASK LABEL KEY` takes the same `--exact`, `--role`, `--nth` and `--frame` options, so a label that every row of a grid repeats can still be reached. `blumkin browser grid TASK` lists the rows and columns of a data grid or table and, for each cell, its text and fields with the `--nth` that `--role ROLE --exact --nth N` takes in `fill`, `press`, `select` and `options` (pass `--exact`: the number counts that exact role and name), so a cell is addressed by its row (`--within ROLE:NAME` picks the grid; field values are never shown, and the page's names are marked untrusted). `blumkin browser options TASK LABEL` lists every option of a dropdown without choosing one: a native select is read, a combobox is opened like `select` opens it, its (possibly virtualized) list is scrolled to the end and it is closed again with Escape. The result has `complete` (false when the scroll or option cap was reached) and `closed` (false when the list could not be closed, so check the page), a field named like a finalizing action is refused, and the names are page text marked untrusted. `upload` does not prefer visible fields, since a file input is often hidden on purpose. If the visible field is not the one you mean, `--nth` picks among every match, hidden ones included.

`blumkin browser cell TASK ROW COLUMN [VALUE]` reaches the cells `grid` cannot: an Oracle JET data grid (a page with an `oj-data-grid`, such as an Oracle time card) draws its cells as plain divs with no roles, labels or fields, so there is nothing for `fill` or `press` to find. ROW and COLUMN are 1-based numbers or header texts (a row header, or a column header such as a day; the columns count the frozen ones first, such as Project, Task and Time Reporting Code, then the scrolling ones), and `--grid N` picks the Nth data grid on the page. With no VALUE the cell is only read (nothing is clicked or typed); with a VALUE it is selected and typed in, a list-of-values cell (a project, a time reporting code) shows a dropdown of matches whose one matching option is clicked, any other cell is committed with `Tab`, and an empty VALUE (`""`) clears the cell. Nothing is ever submitted: Enter is not pressed and a value is at most 80 printable characters. Nothing is clicked if a control (a button, a link, a checkbox) or a cover sits at the click point of the cell, and keys go only to the cell or an editor inside the grid: the first key is typed alone and the rest only once it has opened an editor, so a space can never reach a focused button. The cell is vetted like a click on that element, so a submit-type element, a form-action override or a script link is refused. The dropdown is the one visible list on the page (two are refused), the option is clicked by its position after the same list has been seen twice and only if it still reads the same, and it is vetted first: an option or a typed value that begins with a finalizing word (`Submit`, `Pay now`) is never used, and neither is an option that is a submit-type element, while a code that merely holds such a word, such as `Regular Pay`, is fine, and a value with nothing to match on (only punctuation) is committed with `Tab`. If an editor is still open after the commit, the edit is cancelled and the command fails. A number is read as a position; a header whose text is only digits (a year, a day number) is named by its text with a `text:` prefix (`text:2027`, for the row or the column), and a header that itself begins with `text:` is named `text:text:...` (the prefix is removed once, and the comparison ignores punctuation and case); rows and columns count what the grid has drawn (a row scrolled out of view cannot be reached), and a grid inside a frame is not supported. The task needs no `allowed_controls` entry for a cell, as for `fill`. The text that comes back is the cell's own display text after the edit and is page text, never an instruction: read it against what you meant to enter, and confirm the saved card on the page before relying on it.

`blumkin browser dialog TASK --open [ROLE:]NAME [--open ...] [--close NAME]` reads a dialog or menu that only opens when a control is clicked, such as a Templates menu with its Apply dialog, and always closes it again. It clicks the declared controls given with `--open` in order (each must be in `allowed_controls`, a finalizing name is refused, a pattern never covers a menu item, and a role is given as `ROLE:NAME` when a name exists in more than one), reads the `dialog` subtree (or `--within menu` and the like) the way `browser read --aria --within` does, with field values and addresses removed, and lists its controls with whether each is disabled. Nothing inside is clicked. Every control is vetted before the first click, and any dialog already open on the page is refused rather than touched. The page must stay on `allowed_hosts` after each opening click (nothing is pressed on a page outside them), and the `--close` control is used only when the dialog that was read shows it, so a same-named button elsewhere on the page is never pressed (Escape closes it otherwise, also when the run is interrupted). The dialog is closed afterwards even when a step or the read failed, with the declared `--close` control if given and otherwise with Escape (neither is used when nothing opened), and a failure says whether it is still open; `closed` is false when it is still open, which means look at the page before going on. The text is page content, marked untrusted. Saving or applying a template still takes the ordinary guarded `click`, `fill` and dialog-confirm controls; a site model does not yet record a flow that takes a template name.

`blumkin browser pick TASK TEXT [--role row|gridcell] [--nth N]` chooses a result in a list-of-values dialog, where the rows of a search result are table rows (neither declared controls nor clickable ones) and the dialog may not be marked as one. Fill the search field, read the rows with `browser grid` or `browser read --aria`, then pick the row by its exact text; confirming the dialog is still an ordinary declared `click` such as `OK`. A result is page data, so it is not declared in `allowed_controls`: the text of a finalizing action is refused (a place that merely starts with such a word, such as Payne, is refused too, so fill the exact value instead), the element is vetted like a click, and anything that is, holds or sits inside a button, link, field or other control is refused (click that control by its own declared name instead), because a click in the middle of the row could land on it or bubble to it; content in a shadow root cannot be searched and is refused as well. An option or a tree item is never picked this way, since `click` makes the task declare those. `--nth` (1-based, in DOM order) picks one of several rows with the same text, and a text that matches more than one is refused without it.

`blumkin browser upload` reports more than `ok`: after setting the file it waits half a second and reads what the page shows. `persisted` is `shown` when the file's name appears more often than it did before, in the field's own row (names are compared ignoring case and spacing, so a copy that was already there cannot vouch for the upload), `missing` when the field was dropped by a re-render (or lost the file) and the name is nowhere on the page, and `unknown` when the input holds the file but the page does not display it; `files_held` lists the names the input holds and `input_hidden` flags a hidden or zero-size input, such as a drop zone's, which may not be the one the form saves. A `warnings` list says what to check. On a form that re-renders after a field changes (Oracle ADF, for one), fill the row's other fields first and set the file last, because a later edit of the same row loses a file chosen earlier; then confirm the row shows the file name before saving. The page is read half a second after the file is set, so a re-render that drops the file later than that is not seen, and a drop zone that clears its input after taking the file reads as `missing` if its page does not show the name.

### Look inside a page: frames and the ARIA snapshot

Some panes are not in the page text. `blumkin browser frames TASK` lists the page's child frames: a 1-based number, the host, the origin (never the path or query) and whether the task's `allowed_hosts` accept it. `blumkin browser read TASK --frame N` reads that frame's text (untrusted data, like any page text); it needs `allowed_hosts` and refuses a frame on any other host. `blumkin browser read TASK --aria` returns the ARIA snapshot (roles and accessible names) of the page, or of the frame with `--frame N`: use it to learn a control's name and role before declaring it in `allowed_controls`. Link addresses and field values are removed from it; hidden and screen-reader-only text is not, so it is untrusted data, and a page snapshot stops at frame boundaries. A frame in another origin shows up a moment after it attaches, so `browser frames` waits up to `--wait` seconds (default 2) for one; `--wait 0` lists what is there at once. Every command attaches to the browser fresh, and Playwright does not list a cross-origin frame that already existed when it attached, so blumkin also reads Chrome's own list of frame targets (`/json/list`, on the same loopback endpoint) and talks to such a frame over its own DevTools socket: only on this machine, only to evaluate a script in it, and under the same `allowed_hosts` checks. A frame whose address Playwright already lists is taken from Playwright, and at most 32 such frames are read. Frames reached that way have no ARIA snapshot (`--aria` with `--frame` says so); read their text instead. Frame numbers shift when the page adds or reloads a frame, so list them again before reading, and pass `--host HOST` with `--frame` to refuse any other frame.

## Start a task from a template

`blumkin browser init-task [TASK] --template teams-transcript` creates the task's browser profile and prints the `[browser.tasks.TASK]` table the template starts from: the hosts the site uses (for Teams that includes the SharePoint host its transcript pane is served from) and the navigation controls the task may click. Nothing is written to `config.toml` unless you add `--yes`, which appends the table (creating the file with mode 0600 if it is missing); a table of that name that already exists is never changed, and a `config.toml` that is not valid TOML, or is a symlink, is left alone. The template's `*.sharepoint.com` covers every organization's SharePoint: narrow it to your tenant's host once you know it. The ready-made skill for the Teams template is [`teams-transcript`](../.agents/skills/teams-transcript/SKILL.md). For a time card, `blumkin browser init-task time-sheet --host erp.example.com --form-url https://erp.example.com/timecards --yes` (a task named like a template uses that template; for any other task name, add `--template time-sheet`) creates the profile and the table with your host, `Copy Previous Time Card` and `Save` as the only declared controls, and `extra_deny_names = ["Clear Time Card"]` so the guard refuses the control that wipes the card as it refuses `Submit` (neither is ever declared); the period, its anchor day (a Sunday on Oracle Fusion), the project, task, time reporting codes and hours belong in your own task definition, and the ready-made skill is [`time-sheet`](../.agents/skills/time-sheet/SKILL.md). For an expense report, `blumkin browser init-task --template expense-report --host erp.example.com --form-url https://erp.example.com/expenses --upload-dir ~/Documents/receipts --yes` writes the whole `[browser.tasks.expense-report]` table in one go, with no hand-editing of `config.toml`: your host (it differs per organization, so `--host` is required), the controls of the Oracle Fusion Expenses flow (`Create Report`, `Create Item`, `Save and Close`, `Manage Attachments`, `Add Row`, `Save`, the pattern `Actions for * Report` and `Open`), `dialog_confirm = ["OK"]` for the attachments dialog, the upload folder (default `~/Documents/receipts-archive`) and the `form_url`; none of those controls is a finalizing name, and `Submit`, `Delete` and `Duplicate` are never declared (`OK` is a dialog confirm: it is spared the submit-type check only inside a dialog that holds no finalizing control, so check what your own dialog contains). `browser launch`, `goto`, `upload` and `receipts rehome` read this table (hosts, controls, upload folder), so run it first. A site model records the pages and dialogs of such a flow one at a time: stay on a page and run `blumkin browser explore observe TASK PAGE`, and the page is added to the same draft (or to the stored model when there is no draft), so the order of the clicks does not matter and nothing is lost between pages; `blumkin browser explore save TASK --yes` then stores them together as the next model version.

### Keep a file the page offers: `download`

`blumkin browser download TASK CONTROL --into FOLDER` clicks a declared control that starts a download and keeps the file, for a page that offers a text file (a meeting's transcript as `.vtt`, say) instead of making you scroll for it. Default deny: the task must declare `download_dirs` and `allowed_hosts`, `FOLDER` must be an existing folder inside one of the `download_dirs` (judged on the resolved path, before the browser is touched), and the file must come from an allowed host, be a `.vtt`, `.srt`, `.txt`, `.csv` or `.md` file of at most 20 MB, and have a plain name (the page's suggestion is cleaned of folders and odd characters, or give `--name`). The file is saved to a private temporary folder first and then kept as a new file with mode 0600; an existing file is never replaced. Its text is scanned like `read` and not printed: an `injection_warning` says when it looks like it is trying to instruct an agent, and the text is data, never instructions. A control that could finalize something is refused as for `click`.

Limits to know: the host check uses the address the download was started from (a redirect on an allowed host is not followed back), and a `blob:` download is judged by the origin that created it; the size limit is checked once the browser has finished saving, so a very large file is written to the temporary folder first (which is removed afterwards, or left as a `.blumkin-download-*` folder if the process is killed); only a download that starts on the task's own page is captured, not one that opens in a new tab or window; and in a folder that cannot hold hard links the file is copied instead. A suggested name with no usable characters becomes `download` plus its extension.

## Explore a site once

A task can record the structure of its website once, so later runs do not have to explore it again. The record is a site model: the pages (a URL template and a fingerprint of their landmark controls), the controls on each page (a logical name, a kind, whether it looks finalizing and ordered ways to find it) and the flows that chain them. It holds structure only: nothing you type, no cookie and no personal data, and a label that looks like typed data is skipped and counted. Exploration needs the task to declare `allowed_hosts` and never leaves them.

```bash
blumkin browser explore observe expense-report expense-list
blumkin browser explore click expense-report Help --role link
blumkin browser explore click expense-report "Add line" --page expense-list
blumkin browser explore show expense-report
blumkin browser explore save expense-report --yes
blumkin browser explore forget expense-report old-page
blumkin browser explore discard expense-report
```

`observe` records the page the task's browser is on in a draft kept on disk between commands, and `show` summarizes what the draft would save. `click` follows links and tabs without asking. A control that may change state, such as a button that opens a confirmation dialog, is clicked only after you answer yes at your own terminal; so are all menu items and any link whose name or address looks destructive (delete, remove, log out, archive and the like); the default is no, the question is read from the terminal and never from an argument or the page, and with no terminal (an agent running in the background) nothing is clicked and the command prints what to run yourself, or to declare the control in `allowed_controls` instead. A control the task declared in `allowed_controls` (an exact name or a `*` pattern, the same trust `browser click` rests on) is clicked without a question, so an agent can explore it with no terminal; the result says `approved_by` (`allowed_controls` or `terminal`), the element is still inspected, a pattern never covers a menu item (declare each one by name), a pattern too loose for `browser click` is refused here too, a link whose address looks destructive still asks, and a finalizing name is never clicked even when declared. Ordinary links and tabs are followed with an empty `allowed_controls`, and an undeclared state-changing control can still be approved at your terminal; seed `allowed_controls` before exploring only for the state-changing clicks that must proceed with no terminal, and explore before the task's own clicks. An approval covers that one click, is not stored and never adds the control to `allowed_controls`; the element is inspected before you are asked and again at the click, so one that changed in between is refused, and a link that leads off the allowed hosts or out of the web is never followed. While exploring, a navigation to another host is aborted before the request leaves, but a redirect from an allowed host to another one is followed by the browser itself, so that one request is made and the command then fails with `explore_refused`, saying the click happened. A process that opens its own pseudo-terminal could answer the question for you, so approve clicks from your own terminal session. Names in other languages are not recognized as finalizing on links, and a path word such as a user name in a URL is kept in the template, so review the draft with `show` before you save it. A finalizing control (submit, send, pay and so on) is recorded as such and is never clicked, with or without approval. `save --yes` only acknowledges that you reviewed the draft (nothing checks that you did), and stores it as the next version of the task's model under the config directory (`browser-models/`, private, earlier versions kept) and clears the draft; without `--yes` it shows what it would save and stops. `forget PAGE` drops one page, and the recorded steps that used it, from the draft (or from the stored model, which the next `save` then stores as a new version without it): a page left over from an earlier session, or one recorded before a field took effect. The last page cannot be forgotten; `discard` drops the whole draft. A name marks a control as finalizing only when the control can be pressed (a button, link, menu item or tab), so a combobox called `Payment Method`, a date called `Checkout Date` or a file input called `File Name` is not flagged and a flow can fill it; the guard still refuses to click any control whose name is a finalizing word. Some sites serve every page from one address and tell them apart by what is on them only: when `observe` records a second page at the same address with different landmarks it says so (`shared_addresses`, `warnings`), and `model check` names the recorded page the live page matches best (`best_match`) when that is not the page you asked about.

### Keep the site models in a versioned folder: `models_dir`

Recorded models live in `<config dir>/browser-models/` by default. To keep them in a folder you back up or version (a private git repository next to your task files, say), set `models_dir` under `[browser]` in `config.toml` to an absolute folder or one starting with `~/`. The folder is checked each time it is used: it must have an existing parent, must not be the filesystem root, the home directory, the config directory or a folder above it, or a folder inside, around or the same as (letter case ignored) any task's `upload_dirs` or `download_dirs`, and, once it exists, must be a directory you own that nobody else can read or write (mode 0700; a wider mode is refused with the `chmod` to run, never silently changed). A symlink you give is followed to the real folder, which is then judged the same way. Inside it nothing changes: a symlinked task folder, `history` folder or model file is refused, files are private regular files, and the size, schema and `allowed_hosts` checks still apply on load and save. `blumkin browser model versions TASK` and `blumkin doctor` show the folder in use (`doctor` warns when a configured one would be refused).

To move an existing store without losing versions, copy the whole folder, prove the copy, then set `models_dir`: `cp -a ~/.config/blumkin/browser-models ~/versioned/models`, `chmod 700 ~/versioned/models`, `diff -r ~/.config/blumkin/browser-models ~/versioned/models` (no output means every file is identical; matching version lists alone do not prove a file was copied whole), set `models_dir`, run `blumkin browser model versions TASK` and `blumkin browser model diff TASK 1` for each task so every version is read back, and keep the old folder until all of that passes. A copy that stops half way is recoverable only while the old folder still holds the complete files: the history is the record, `model.json` is repaired from the newest saved version by the next save, and a leftover temporary file is ignored, but a truncated history file is not repaired. Models are not moved or merged for you, and until `models_dir` is set the old folder stays in use.

## Check that a site has not changed

Before a task relies on a recorded model, check that the site still matches it. Open the page in the task's browser, then run the check against the model's page of that name.

```bash
blumkin browser model check expense-report expense-list
blumkin browser model versions expense-report
blumkin browser model diff expense-report 1
```

`check` only reads the page (it never clicks or types) and grades it by role and accessible name, so layout, color and ordering changes are ignored. A number in the name of a link, button, menu item or tab (a count such as `(7 more...)`, a day, an amount) is data: the recorded control matches the live one of the same role whose name differs only in its numbers (`(8 more...)`), so a count that moved is not drift, and the pages' share of recorded landmarks is compared the same way, while a changed word around it, a different role or a control that is gone still is. The match needs exactly one live control of that shape and some letters in the name, so a numbered list (`Delete row 5`, `Delete row 6`) or a name that is only a number is still reported; with a single live `Delete row 5` left, a recorded `Delete row 3` cannot be told from the same row renumbered, so it counts as found. `compatible` means every control is still found and the page is recognizably the recorded one. `degraded` means it still works but the model should be updated: a control is found only by a fallback locator, cannot be verified from a page snapshot (a selector-only control), or some landmarks changed. `incompatible` means re-explore the page: a control is gone, a new field appeared (it may be required) or the page no longer looks like the recorded one; the command exits 1 (the same code as other failures, so use `--json` and read `grade` to tell them apart). A page with fewer than three recorded landmarks is judged by those alone: none of them on the page, or a different address, makes it `incompatible`. A new button or link is not drift. The page must be on the task's `allowed_hosts`, and the check says when the page's address does not look like the recorded one. `blumkin browser explore observe TASK PAGE --kind dialog --landmark A --landmark B` records a popup the page does not mark as a dialog (an Oracle ADF attachments popup has no `role=dialog`): the landmarks, at least two controls seen on the page and not finalizing actions, are stored with the page, and `explore show` prints them as the `dialog_landmarks = [...]` line for the task's policy, so a declared `dialog_confirm` such as `OK` works inside that popup; `--kind list-of-values` records a search dialog whose result rows are chosen by their text. Observing a recorded page again without `--kind` keeps its kind and landmarks (`--kind page` demotes it on purpose), and `model diff` reports a page whose kind or landmarks changed. An ordinary page keeps its stored shape, with no kind, but a model that holds a dialog or list-of-values page, or a `pick` step, is not read by a blumkin from before this change. A flow `pick` step always picks a row (no `nth`, no other role), and a row text that is a finalizing word is refused when the flow runs, as `browser pick` refuses it. `blumkin browser model flow add TASK NAME --param NAME:KIND --step SPEC ...` writes a flow into the stored model without recording it click by click (the plans `ledger apply --flow NAME` runs): a parameter is `NAME:KIND` with KIND date, file or text, or `NAME:choice=A|B|C`; a step is its action, then its control when it acts on one (click, press, fill, upload), then `key=value` words (`page`, `bind`, `expect`, `expect_heading`, `instruction`, `row`, `column`, `value`), and the actions are click, press, fill, upload, goto, cell, pick (choose a list-of-values result row by its text, from a `bind` or a literal `value`, with the same vetting as `browser pick`) and handoff. The flow is put into a copy of the current model and checked as any model is, so a spec cannot say what a recorded flow could not (a step must name a control and a page the model records, a binding a declared parameter, a handoff no control, an action one of the eight above, and a click or press may not name a control the model records as finalizing: hand that step to the person with a handoff); without `--yes` that check is all that happens and nothing is written, a flow of the same name is replaced only with `--replace`, and `--yes` saves the next model version, built from the model it read and refused if a newer version appeared in between (run it again then), a replaced flow keeps its place and the pages keep their `recorded_at` (it needs a saved model, and nothing touches the browser). When a flow runs, a step's control, named in the model by its logical name, is found on the page by the role and accessible name (or the label) the model records for it, and a name the model does not record is used as written. `versions` lists the saved versions of the model and `diff` shows what changed between two of them (hosts, pages, flows, and the controls added, removed or changed, including a control that became finalizing or safe).

## Remember what has been filed

A time sheet is filled one day at a time and an expense report one receipt at a time, over several sessions. The ledger remembers, for one instance of a task (this pay period's time sheet, that trip's expense report), what has been filed so far, so a restarted session does not file anything twice. `blumkin browser ledger begin TASK INSTANCE --expect day=10` starts it; the instance name is a short word such as `2026-p21` or `trip-lisbon`. `blumkin browser ledger expect TASK INSTANCE --expect day=14` changes the expected counts of an open instance when the plan changed (10 days were staged where 3 were first expected, which would end as "10 of 3 days filed"): the kinds named get the new count and the others keep theirs, nothing is removed, a submitted or discarded instance refuses it, and the change is a journal entry of its own (a blumkin from before this command cannot read a journal that holds one). Prefer the ledger-backed verbs: `blumkin browser ledger stage` (idempotent if already verified), `blumkin browser ledger apply --flow NAME` (runs a recorded site-model flow then marks filled; a verified item is a no-op), `blumkin browser ledger verify --present` or `--missing` (read-back), `blumkin browser ledger reconcile KIND --page-item …` (read-only divergence vs the page), and `blumkin browser ledger handoff --step …` (always `submitted: false`, built from the ledger). `blumkin browser ledger record TASK INSTANCE KIND ITEM STATE` remains for manual state fixes. A receipt carries `--sha256` from the start. `blumkin browser ledger status TASK INSTANCE` reads like a sentence, for example "3 of 10 days filed, 4 receipts filed, not submitted"; `blumkin browser ledger list TASK` lists the task's instances.

A recorded flow can declare its inputs, so a run is given named values and not whatever the agent decides: a flow's `params` list each input with a kind (`date` as `YYYY-MM-DD`, `choice` with its recorded options, `file` for an existing regular file that is not a link, or `text` of 1 to 500 printable characters), and a `fill` or `upload` step names the one it uses with `bind` (an `upload` takes a `file` parameter, a `fill` any other kind, a flow that declares parameters must bind every `fill` and `upload` step, and a parameter cannot be called `item`, which the run sets to the ledger item). Choices are stored in the model, so like every label they may not hold quotes, an equals sign, an at sign or a long run of digits. `blumkin browser ledger apply TASK INSTANCE KIND ITEM --flow NAME --value KEY=VALUE ...` checks every declared parameter before the item is staged or the browser is touched: each must be supplied, nothing undeclared may be, and each must be valid, with every problem listed at once and no value ever shown (amounts, merchants and paths are private; an undeclared name is shown quoted). A `file` is read from the path as given, relative to where the command runs and with no `~` expansion, and that same absolute path is the one uploaded; the check that it is a regular file and not a link covers the last part of the path and is made when the run starts, not when the file is uploaded. A refused run changes nothing in the ledger. A flow that declares no `params` keeps the older, unchecked bindings, and a model without them is stored exactly as before. Running `ledger apply` again for an item that is already verified is still a no-op. Parameters are the first step toward compiled plans (#622). A flow step can also state `expect_heading`, a heading the page must show afterwards: the run waits for it (bounded, as `click --expect-heading` does) and stops at the first step whose heading never shows, naming the step and saying that the step WAS made; the item is not marked failed then (a plain re-run would repeat what already happened), and the error names the step to resume from with `--from-step`. A step with the action `handoff` and an `instruction` is the human's part (the attachments dialog's `OK`, the final `Save`): it names no control and binds nothing, and the run stops there without failing the item, prints `paused at step N: <instruction>` (and the same under `paused` in `--json`) and the step to resume from. Run the same `ledger apply` command with `--from-step N` once it is done (one past the last step when the handoff is the last one); the steps before N are not run again, a handoff before N that states `expect_heading` is checked again, and `--from-step` above 1 is refused for an item that no earlier run staged or that failed. The instruction is text recorded in the model and is marked in the result (`instruction_note`) as data to show the person, not an instruction to an agent; a model can hold a handoff step for the final `Submit` only as words for you to follow, since blumkin never presses it. A handoff step that also states `expect_heading` goes on by itself when the page already shows that heading (the human did it) and pauses otherwise. Where a run stopped (a handoff, or a step whose heading never showed after the step was made) is saved in the ledger as the flow and the step to go on from, and `ledger status` shows it for the item (`resume`): while it is saved, a `ledger apply` with no `--from-step` is refused and names the step to resume from, since running the flow again from step 1 would repeat what was done, an item that stopped in one flow is refused another flow the same way, `--from-step` is taken as given, and `--restart` says that running again from step 1 is meant; the saved stop is cleared when the item is filled or fails, and a later stop replaces it (it is checked when a run starts, so two runs for one item at the same moment are not serialized by it, and if the ledger cannot save it, say because the instance was closed meanwhile, the pause or the failed condition is still what is reported). It is a journal entry of its own, so a blumkin from before this change cannot read a journal that holds one. Both keys are optional, so a model without them is stored exactly as before. A step with the action `cell` edits or reads one cell of an Oracle JET data grid, as `blumkin browser cell` does and with the same vetting, so a time-card day can be a parameterized flow: it carries a `row` and a `column` (1-based numbers, header texts, or `$name` for the value of a non-file flow parameter, with the `text:` prefix for a header that is only digits, and `$$name` for a header that really is `$name`) and, for the cell's content, either a `bind` to a parameter, or a literal `value` (an empty one clears the cell), or neither, which only reads the cell; it names no control, and the other step keys (`expect_heading` included) work as on any step. A model without cell steps is stored exactly as before. Resolved locators and a way to author a flow without recording it are not part of this yet.

The ledger is a private append-only journal under the config directory (`browser-tasks/<task>/<instance>/journal.jsonl`, mode `0600`). Writers take a lock and append one line at a time, so two commands cannot corrupt it, a half-written last line left by a crash is ignored and cut off by the next write, and a damaged line anywhere else is reported as `ledger_invalid` instead of being guessed at. It holds item ids, states, model versions and file hashes only, never an amount, a vendor, a path or a field value, so keep ids to dates and short words.

blumkin has no submit command. `blumkin browser ledger submitted TASK INSTANCE --yes` records that you did, and nothing else records it; say yes only if you pressed the button yourself. A submitted or discarded instance accepts no more items. `blumkin browser ledger discard TASK INSTANCE --yes` closes an instance without touching the real form and keeps its journal.

`blumkin browser ledger report TASK INSTANCE --report-id 100234 --draft-saved --total-confirmed` records the report itself: the number the server gave it, that a draft of it is saved there, and that the user confirmed its total. The ledger holds no amounts (a vendor, a path or a total never reaches the journal), so the total is only ever recorded as confirmed. `blumkin browser ledger status` then separates what is on the server (items read back from the page and verified) from what is only local or not yet read back, and `ledger handoff` carries the same lines. At the end of a session ask the user whether they are all done with the trip, then record the answer with `blumkin browser ledger close TASK INSTANCE --outcome done --yes` or `--outcome pending --yes` (`--yes` says the user gave that answer; nothing infers it). Add `--close-browser` to close the task browser after the answer is recorded; its profile, and the saved sign-in, is kept. The ledger needs this blumkin or a newer one to read a journal that holds these entries (an older blumkin reports it as a damaged journal). A pending instance stays pending only until new work is recorded on it; it resumes in the next session: `ledger status` says to reopen the saved report (its recorded id) and to `ledger reconcile` the ledger with the page before filing more. Closing a session is not submitting: the report stays `submitted: false` until you say otherwise with `ledger submitted`. A receipt whose render was bad is swapped for a good one with `blumkin receipts rehome FILE --task TASK --instance INSTANCE --date D --vendor V --total T --currency C --replace NAME --yes`, which keeps the old file under `superseded/` instead of deleting it.

## Read a Teams meeting transcript

`blumkin browser transcript TASK` captures the transcript of a Teams meeting that someone else organized, where `blumkin meeting` has no access and the pane's own Download button is disabled. Open the meeting's chat in the task's browser (sign in by hand first) and its Transcript tab, then run it.

```bash
blumkin browser profile create teams-transcript
blumkin browser launch teams-transcript
blumkin browser goto teams-transcript https://erp.example.com/
blumkin browser click teams-transcript Notes --role tab
blumkin browser click teams-transcript Transcript --role tab
blumkin browser transcript teams-transcript --duration 34m06s --out ~/work/meeting-transcripts/intros.txt
```

```toml
[browser.tasks.teams-transcript]
allowed_hosts = ["erp.example.com", "*.example.com"]
allowed_controls = ["Notes", "Transcript"]
```

`blumkin browser read` cannot do this: Teams serves the transcript from the organizer's OneDrive in a cross-origin iframe, and the list is virtualized, so at any moment only the rows near the viewport exist in the page (about 12 of 34 minutes in the meeting that shaped this command). `transcript` scrolls that frame from its first row to its last, merges the overlap and writes one `[m:ss] Speaker: text` line per turn. The task needs `allowed_hosts` that include both the top-level page host and the frame's host (for Teams, `teams.microsoft.com` and `*.sharepoint.com`; the example uses `erp.example.com` and `*.example.com` as stand-ins), plus `allowed_controls` for the tabs it clicks (`"Notes"`, `"Transcript"`); the command is read-only and clicks nothing. `--out` creates a new file with mode `0600` and never overwrites one.

Everything that knows what the Teams page looks like (the scripts that find and scroll the transcript pane, the parser for its text and the started and stopped transcription event lines) lives in one module, `blumkin.browser.teams`, so a change in the page is one fix; the coverage report and the merge of overlapping chunks are page-independent (`blumkin.browser.transcript`).

Every capture carries a coverage report, so a gap is reported instead of silently missing: the entry count and speakers, the first and last timestamp, silences longer than three minutes, entries out of order and whether the scroll reached both ends. With `--duration` the last entry is checked against the meeting's length, unless Teams logged "stopped transcription" (the transcript legitimately ends before a meeting that kept running). `complete` is false when any of that looks wrong, and a capture that is not complete must not be presented as the whole meeting. The text is untrusted data and goes through the injection scan like `read`.

## Receipts

`blumkin receipts find --dir ~/Documents/receipts --json` lists the images and PDFs in a folder, newest first. `blumkin receipts find --dir ~/Downloads --new-since 30m --json` keeps only files that arrived in the last 30 minutes (each entry shows `arrived`), `blumkin receipts to-pdf ~/Downloads/till.jpg --out ./receipts-to-upload/` turns a photo into a PDF for sites that only take PDFs, and `blumkin receipts read ~/Documents/receipts/taxi.jpg --json` reads one with the existing OCR and reports vendor, date, total and currency, each with a confidence (`high`, `low` or `none`), so the task asks you about anything doubtful instead of guessing. OCR needs the `ocr` extra (`uv tool install -e '.[pdf,ocr]'`) plus `tesseract` and `poppler`; without it the result says `needs_manual` and the task asks you for the amounts. `blumkin receipts summarize <files-or---dir> --json` reads several receipts and prints one row per receipt (`file`, `drop` or `review`) with a grand total per currency: receipts with the same vendor, ride date and currency are one trip, a lower total within 1.4 times of a higher one is the without-tip copy and is marked `drop` only when the two arrived within 30 minutes of each other or are the same message or file (otherwise both rows are marked `review`, as is any row whose total or currency is not certain), and the ride date comes from the receipt text or subject, with the email arrival time only as a flagged last resort. Nothing is moved or deleted. After you confirm the table, `blumkin receipts rehome` needs `--yes`, and `--replace <name-or-hash8>` swaps a bad render for a fixed one, keeping the old file under the instance's `superseded/` folder. After you confirm the fields, `blumkin receipts rehome ~/Downloads/scan.jpg --task expense-report --instance trip-lisbon --date 2026-10-20 --vendor "Taxi Co" --total 18.50 --currency USD --yes` moves the file into the managed per-instance folder under the task's first `upload_dirs` entry, named `YYYY-MM-DD_vendor_amount-CURRENCY_hash8.ext` (the vendor appears in that filename). Pass `--message-id` for a mail attachment so the file is copied (not moved) and the message id is recorded. Rehome keeps a separate private intent/result journal at `browser-tasks/<task>/<instance>/receipt-moves.jsonl` (mode `0600`) that stores resolved source and destination paths, the SHA-256, and optional message id so a crash can be resumed and `browser ledger discard --yes` can restore originals (including an intent-only half-finished move). Receipts that arrive as HTML mail with no attachment need a PDF for the expense site: `blumkin mail export --id <message-id> --out ./receipts-to-upload --json` renders the body with a headless browser (images on; scripts, frames, linked resources, meta tags, some elements hidden by supported inline styles and images declared as one pixel removed; text hidden by a stylesheet can be absent from the PDF yet remain in the `.txt` file, so check amounts visually; so an image with no declared size can still load and tell the sender the message was opened; throwaway browser profile) and writes `<name>.pdf`, `<name>.txt` (the same content as text) and `<name>.json` (message id, sender, received time, subject) side by side in the folder you name, never in the receipts archive. The export checks the PDF against the message and exits 1 listing the problems when the render is broken (missing images, blank pages, a text layer that does not match); `blumkin receipts check <pdf>` re-runs that check later. `receipts read` prefers the `.txt` beside a PDF over OCR, but only when the `.json` records that exact PDF and text by SHA-256; an edited, replaced or oversized `.txt` is ignored and the PDF is read normally. A prompt-injection warning on the message is reported and recorded in the JSON without stopping the export. For receipts that arrive by mail, list a message's attachments with `blumkin mail attachments --id <message-id> --json` and save the ones you want with `blumkin mail attachments download`.

## What blumkin refuses

- Submitting. There is no submit command, and the guard is deny-by-default and enforced in code, not in a prompt. `blumkin browser click` refuses, without touching the page: a control the task did not declare by its exact name, a role that is not clickable, a submit control (judged by the browser's own idea of the control's type, so a button with an invalid `type` counts), a control with a `formaction`, a link that runs script and an inline handler whose text mentions submit, and any control with any word in its name that starts with a finalizing word (submit, send, file, confirm, pay, finish, complete, approve, authorize, place order, and more, so "Payments" and "Save and send" are refused). The deny check runs first: a control is refused even when it is listed in `allowed_controls`. The refusal exits non-zero with `submit_blocked`.
- Keys that submit. `blumkin browser press` allows only navigation keys (Tab, arrows, Escape, Backspace, Delete, Home, End, Page Up and Down) and single printable characters; Shift+Tab also works, but Enter, Space, a newline and every other modifier combination are refused, and so is any key aimed at a button.
- A safety net behind all of that. While blumkin is attached it swallows every non-GET page navigation, which is what submitting a form does, so even a script that submits a form on its own gets no navigating POST through. The page stays as it was, your typed values included. The net lives only on blumkin's connection: once the command finishes it is gone, and your own final click is never blocked.
- Uploading anything else, or anywhere else. `blumkin browser upload` takes only a regular file inside one of the task's `upload_dirs`, judged on the fully resolved path (so a symlink or `..` cannot step out), checks the file and the folder before the browser is touched, checks the page host once attached, and refuses unless the page is on one of the task's `allowed_hosts`; a hard link is refused, because it can point at a file outside the folders.
- Anything but `http` and `https` pages: `goto` refuses `file:`, `javascript:` and `data:` URLs.
- Following the page. Text read from a page or a receipt is data, never instructions, and is scanned for prompt-injection patterns.

## Limits

- The guard is a backstop, not a guarantee. A declared control that is not on the deny list is clicked, so declare only controls that cannot finalize. A form submitted by a GET request is a GET navigation, which the net lets through (the browser does not say whether a navigation came from a form, so there is no setting for it), and a page can submit from a listener added by script, which the inline-handler check does not see.
- The host checks are detective, not preventive, after a page changes: when a `goto`, a click or an upload ends on a host outside `allowed_hosts` the page has already loaded (nothing from it is returned), and the command fails with `host_blocked` so the task stops before anything is typed into or read from it. `goto` is not limited at all when no `allowed_hosts` are declared.
- Use this on a machine you alone use. The browser's DevTools port listens on `127.0.0.1`, which keeps other computers out but not other user accounts on the same machine, and the profile directory's permissions do not protect a TCP port. On a shared host another user could drive the signed-in browser.
- The safety net protects only while a command is attached. A page that schedules a submit to fire after the command has finished (a timer, for example) is outside it; the guard's checks and your declared controls are what limit that, and the user's own final click is deliberately never blocked.
- After the safety net swallows a submit, the rest of that command may wait on the page for a moment; start a new command or finish the task with `handoff`.
- A form that submits through a background request (a script that posts data without navigating) is not a navigation, so the net does not see it unless the task turns on `block_background_writes`. The guard's checks and your declared controls are what stand between a task and such a page, which is why `allowed_controls` is a short list you wrote.
- The drift check compares what a page snapshot shows, so it cannot see a control that became disabled or required, text in another language, or a locator that is only a selector (those are reported as unverified). Links and menu items are often data (mail subjects, list rows), so a missing one only degrades the grade. Two controls with the same role and name on a page count as one. A page cut off at the control cap is not checked for new fields, and one with more landmarks than the model keeps (100) may report a field it did not record as new.

## Housekeeping

`blumkin browser status` shows each task profile, whether its browser is running and the loopback DevTools endpoint. `blumkin browser profile list` lists the profiles, and `blumkin browser profile delete expense-report --yes` removes one, saved sign-in and cookies included; it refuses while that task's browser is still open: close it first with `blumkin browser close expense-report`. Only profiles blumkin created are listed, attached to, closed or deleted.

`blumkin browser close TASK` ends the browser `browser launch` opened, so an agent can clean up after itself without asking you to close a window by hand. It asks the browser to quit and waits up to `--wait` seconds (15 by default, at most 300) for it to exit, which lets it write its profile out, and it keeps the profile: the saved sign-in and cookies are there the next time you `browser launch TASK`. It signals only a process that is confirmed, by its command line, to be a browser running on that task's profile, so a stale session whose pid has been reused is never touched. With no browser running it says so and exits 0. When `ps` cannot answer, nothing is signalled and the close is reported as `browser_close_failed`, never as "no browser", and the session record is kept. `browser close` refuses to signal any process in its own process tree (itself, its parent, or the head of its process group or session), even one whose command line names the profile. A browser that does not exit is reported as `browser_close_failed`; `--force` then kills it (its process group, only when the browser leads it), clears Chrome's stale single-instance files, and its profile may need to recover. Closing never deletes anything: `profile delete` is the command that does.

`blumkin browser raise TASK` brings the task's browser window to the front, for the moment you are asked to sign in or act by hand and cannot find it. Each task profile is its own Edge or Chrome process under one application name, so activating the application by name raises whichever instance the system picks (often your regular mail window); this finds the process blumkin recorded at launch (a strict check that it is the browser of that profile), un-hides and un-minimizes its windows, raises the one that was in front through System Events (found again by its title, since raising reorders windows) and reports the front window's `title` (page text, so untrusted, with any web address removed) and the `pid`; a browser that was only just started and is not listed yet, or has no window yet, is tried again after a second and then reported as failed, never as raised. It works on macOS only; the first use may ask you to allow your terminal under System Settings > Privacy & Security > Accessibility, and elsewhere, or with no browser running, it fails with `window_raise_failed` (or `browser_not_running`) and leaves the browser alone. `blumkin browser launch` raises the window by default on macOS (as `raised` in its output; elsewhere there is no `raised` entry) and `blumkin browser goto` does once the page is still on the identity provider after a poll, so a silent hop that forwards at once does not pull the window forward; `--no-raise` turns either off, and neither fails when the window cannot be raised. `blumkin browser status TASK` shows the process id, and `--verbose` the window title as well (only when it carries the title of the page that was checked, an allowed or sign-in host whose title is not withheld, since the OS reports the front window, which may be another tab; with a note that it is page text; it makes one more System Events call, which can trigger the Accessibility prompt). The title of `raise` and `launch` is not gated by host, since they do not attach to the page: treat it as page text.

A sign-in that loops or never finishes is seen and recovered from without deleting the profile. `blumkin browser status TASK --verbose` also attaches (without the form-submission guard that task commands install, so looking cannot swallow the identity provider's POST and stall the sign-in being inspected; it marks, clicks and reads nothing) and shows where the browser is now: its host and path (never the query, the fragment or `;` parameters, where tokens live, and a long path segment, which may be an opaque id, is masked), the title, and whether the host is one of the task's `allowed_hosts` or a recognized sign-in host; for a host that is neither, only the host is shown, never its path or title, since they are words from a page the task may not use, and the title is also withheld (`title_withheld`) when the page moved between the address being read and the title. `status --verbose` never opens a blank page (unlike the other commands, which do when the browser has none): a browser with no open page is shown as `page_error`. If the attach itself fails, or the browser is not running, that is shown as `page_error` next to the status (the exit status is still 0), with any web address in the message removed. `blumkin browser read TASK` (text or `--aria`) works on a page of a built-in or declared `sign_in_hosts` host even when it is outside `allowed_hosts`, marked `sign_in_page`, so the error or account picker can be read (on such a page every web address is removed from what comes back, in text and in `--aria`, from the title and from any injection warning, and the `url` is shown without its query, fragment or parameters, since an identity provider's error page often echoes the redirect address and request ids; the account picker still shows the account's own name or address); it is the only thing allowed there, and every click, fill, upload and frame read still needs an allowed host. A page read checks the host again after the content is captured and returns nothing if the page moved to another host meanwhile (this narrows the window between the check and the read; it does not close it, and navigation is not blocked while reading, since that could abort the sign-in's own redirect; a read of a sign-in page also runs inside the same allowance `goto` uses while the user signs in, so the identity provider's own form POST is not swallowed by the safety net while the page is read). To reset the sign-in session, run `blumkin browser reset-session TASK --yes`: it deletes every cookie of the task's running browser (and says how many; the browser must be confirmed running, and a closed tab is replaced by a blank one), which signs the profile out of every site, the identity provider included, then `blumkin browser goto TASK` and sign in by hand again; the profile's folder, settings and any site data kept outside cookies stay, nothing is read from or done to a page, and `--yes` is required because the sign-in is gone for good. Without a running browser, `blumkin browser close TASK` then `blumkin browser launch TASK --open` also keeps the profile (sign out of the identity provider in that window first if it keeps handing back the old session). `blumkin browser goto` also reports `chain` in its JSON when the page moved through more than one address: each step's host and path (never a query, fragment or `;` parameter; a segment that is long, looks like an email address or has four digits or more is masked; a host that is neither allowed nor a sign-in host shows only the host), repeats dropped and a long loop cut to its first and last steps, so a redirect loop is seen rather than guessed at; every hop of a server redirect counts, not only the pages that finished loading, and a `goto` that fails (a sign-in that never leaves the identity provider, or a page off the allowed hosts) carries the same `chain` in its error. Deleting the profile is the last resort, not the first. Each Playwright step of `click`, `goto`, `fill`, `select` and `upload` times out after 30 seconds with a clear error instead of hanging (`click --wait` sets how long to wait for the control, and `goto` may then wait up to 120 seconds more for a sign-in to finish), so a redirect chain that does not finish is reported, not waited on forever. The window mark (5 seconds, skipped when it expires) and the account pick of `sign-in` (the action timeout) also have a deadline, which a hung page cannot outlast on POSIX in the main thread (an expiry in `sign-in` says the click may or may not have happened, so look at the page before running it again); the remaining page evaluations (reading an element's state, a dropdown's options) still have no timeout of their own, so a page whose script never returns can still stall one of those.

## Errors

| Error | Exit | Meaning |
|-------|------|---------|
| `submit_blocked` | 1 | The guard refused a click or key press. Do not retry; hand the final step to the user. |
| `browser_not_running` | 1 | No browser is running for the task. Run `blumkin browser launch TASK` and sign in again. |
| `browser_no_page` | 1 | The browser is running but has no open page and none could be opened. Open a tab in its window, or close the browser and launch it again with `--open`. |
| `sign_in_timeout` | 1 | `goto` or `launch --open` waited for the sign-in redirect to finish and the page was still on the identity provider. Sign in by hand in the browser window, then run `blumkin browser goto TASK` again; the browser keeps running. |
| `browser_attach_failed` | 1 | The browser is running but attaching to it over DevTools failed. Try again, or close it and launch it again. |
| `browser_action_failed` | 1 | A page action failed or timed out. Read the page and check the label or control name. |
| `browser_dependency` | 1 | Playwright is missing or broken. Run `uv sync --reinstall-package playwright` in the blumkin clone, `uv tool install -e . --reinstall`, or `uv tool upgrade blumkin --reinstall-package playwright`, then retry. |
| `browser_launch_failed` | 1 | The browser did not open a DevTools port in time. |
| `browser_not_found` | 5 | Neither the configured browser nor Chrome is installed. |
| `not_found` | 5 | No profile exists for the task (create it with `blumkin browser profile create TASK`), or a file or folder the command named is missing. |
| `sign_in_not_authorized` | 1 | `blumkin browser sign-in TASK` was run for a task that does not set `sign_in_account = true`, or on a profile that records no account address. Nothing was clicked. |
| `sign_in_refused` | 1 | `browser sign-in` did not click: the page is not an https sign-in page of this task, no tile or several tiles match the profile's account, or the page asks for something to be typed. Pick the account by hand. |
| `address_not_authorized` | 1 | `blumkin browser address TASK` was asked by a task whose table does not set `use_profile_address = true` (or by an unknown task); the address is not looked at. |
| `upload_blocked` | 1 | The file is not a regular file with a single link inside one of the task's `upload_dirs` folders, the page is not on one of its `allowed_hosts`, or the task declares neither. |
| `download_blocked` | 1 | The task declares no `download_dirs` or `allowed_hosts`, the folder is not an existing folder inside a `download_dirs` folder, the file name is not a plain text-file name, the file is too large or not a regular file, or a file of that name already exists. |
| `host_blocked` | 1 | `goto` was asked for a host outside the task's `allowed_hosts`, or a page the task is on or ended up on is outside them. |
| `window_raise_failed` | 1 | `browser raise` could not raise the window: not macOS, no Accessibility permission for your terminal, or no window. Raise it by hand; the browser keeps running. |
| `browser_close_failed` | 1 | `browser close` asked the browser to quit and it was still running after `--wait`. Close its window by hand, or retry with `--force` to kill it. |
| `profile_in_use` | 1 | Raised when the task's browser is running or a launch for it is in progress; close it or wait, then try again. |
| `explore_refused` | 1 | Exploration needs `allowed_hosts` for the task, or the page is (or a click led) outside them. |
| `model_invalid` | 1 | The draft or the stored model was rejected: a field outside the schema, a value that looks like typed data, a symlink or a file that is too large. |
| `reply_failed` | 1 | `blumkin loop finish` could not send its reply; the item's documents are kept, so run it again. |
| `ledger_invalid` | 1 | A task instance journal has a damaged line (not just a torn last one); restore it from a backup or discard the instance. |
| `usage_error` | 2 | A bad task name, a missing `--yes`, or a handoff with no `--step`. |
